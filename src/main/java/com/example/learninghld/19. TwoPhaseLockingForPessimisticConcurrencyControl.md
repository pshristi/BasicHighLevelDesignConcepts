## **Two-Phase Locking (2PL) for Concurrency Control**

Two-Phase Locking (2PL) is a concurrency control protocol that ensures serializability in database transactions. It's a pessimistic approach that prevents conflicts by acquiring locks before accessing data and following a specific pattern of lock acquisition and release.

### **Basic Two Phase Locking:**

- Phase1: Growing Phase
  - Txn request for the lock by Lock manager.
  - Lock Manager either grant or denied the lock request (denied if other txn has placed the locked on it already)
  - **Additional Details**:
    - Transaction can only acquire locks, not release any
    - Different types of locks may be acquired (shared, exclusive)
    - Lock requests are queued if they cannot be granted immediately
    - The transaction is blocked until all requested locks are acquired

- Phase2: Shrinking Phase
  - Txn can not acquire any new locks.
  - Txn is only allowed to release the lock which is taken previously.
  - **Additional Details**:
    - Once a transaction releases any lock, it enters shrinking phase
    - No new locks can be acquired in this phase
    - Locks are typically released when transaction commits or aborts
    - The order of lock release doesn't matter for correctness

### **How 2PL Ensures Serializability**

- **Lock Compatibility Matrix**:
  - Shared locks (S) are compatible with other shared locks
  - Exclusive locks (X) are not compatible with any other locks
  - This ensures read operations can proceed in parallel
  - Write operations require exclusive access

- **Conflict Serialization**:
  - 2PL guarantees that conflicting operations are ordered
  - If transaction T1 and T2 access the same data item, and at least one is a write:
    - Either T1 gets all its locks before T2 releases any
    - Or T2 gets all its locks before T1 releases any
  - This creates a serialization order between transactions

- **Example Scenario**:
  - T1 wants to read and update account A
  - T2 wants to read and update account B
  - T1 acquires S lock on A, upgrades to X lock, updates A
  - T2 acquires S lock on B, upgrades to X lock, updates B
  - Both transactions can proceed concurrently
  - If both wanted to access the same account, one would wait

### **2 big issues with basic 2PL and its work around**
- Deadlock
- Cascading Aborts

### **Performance Considerations**

- **Concurrency Level**:
  - 2PL allows for concurrent execution of non-conflicting transactions
  - Lock granularity affects concurrency (row-level vs. table-level)
  - Fine-grained locking increases concurrency but adds overhead
  - Coarse-grained locking reduces overhead but limits concurrency

- **Lock Management Overhead**:
  - Maintaining lock tables
  - Processing lock requests and releases
  - Detecting deadlocks
  - Memory requirements for lock information

- **Transaction Throughput**:
  - Affected by lock contention
  - Influenced by transaction mix (read-heavy vs. write-heavy)
  - Impact of transaction duration on lock holding times
  - Trade-off between consistency and performance

### **Deadlock in 2PL**

A deadlock occurs when two or more transactions are waiting for each other to release locks, resulting in a circular wait condition where none can proceed.

![img_2.png](../../../../resources/img_37.png)

**Deadlock Example**:
- Transaction T1 holds a lock on resource A and requests a lock on resource B
- Transaction T2 holds a lock on resource B and requests a lock on resource A
- Neither transaction can proceed, creating a deadlock
- Without intervention, both transactions would wait indefinitely

**Impact of Deadlocks**:
- Blocked transactions consume system resources
- Reduced throughput and performance
- Poor user experience due to hanging transactions
- Potential system-wide performance degradation

### **Deadlock Prevention Strategies:**

- Timeout:
  - In this strategy, scheduler find out that TXN is waiting too long for the lock, it simply assumes that there might be a deadlock involving this transaction and thus abort it. 
  - Schedule can make mistake (what if TXN1 wait for the lock, which is acquired by other TXN2 which is taking just long time to finish).
  - **Implementation Details**:
    - Set appropriate timeout values based on typical transaction duration
    - May use adaptive timeouts based on system load
    - Can implement exponential backoff for retries
    - Simple to implement but potentially wasteful
  - **Real-world Usage**:
    - Common in distributed databases where deadlock detection is expensive
    - Used in high-throughput systems where occasional unnecessary aborts are acceptable
    - Often combined with other strategies for better results

- Direct graph called Wait-for-Graph(WFG):
  - There will be an edge from node Ti to Tj.
  - Scheduler delete the edge, whenever lock is release by particular txn which causing some other txn to wait. 
  - Scheduler looks for cycle in the WFG and try to identify the deadlock. 
  - When deadlock is identified, TXN is chosen from the cycle in WFG that need to be ABORTED (these txns are called victim)
  - Scheduler check below things to identify the victim:
    - The amount of effort txn has put till now
    - The amount of effort required to finish the txn
    - The cost of Aborting the txn (cost generally means here is how many updates already has been done)
    - The number of cycles that contains the transaction.
  - **Implementation Details**:
    - Graph is updated whenever locks are requested or released
    - Cycle detection algorithms (e.g., depth-first search) are run periodically
    - Can be implemented centrally or in a distributed manner
    - More accurate than timeout-based approaches
  - **Challenges in Distributed Systems**:
    - Maintaining a global wait-for graph is difficult
    - Communication overhead for graph updates
    - Partial information may lead to missed deadlocks
    - Potential inconsistencies in distributed detection

- Conservative 2PL (also know as Static 2PL): 
  - Avoid deadlock by requiring each txn to aquire all the locks at start of the txn itself.
  - Each txn, predaclared its Read and Write operation to the scheduler.
  - Scheduler tries to set all the lock needed by txn.
  - If Scheulder fails to acquire any lock, none of the lock will be granted to Txn and it will wait.
  - Cons of Conservative 2PL:
     - Less concurrency
     - Extra overhead for Scheduler to know all the Read and Write operation of txn before starting the operation.
  - **Implementation Details**:
     - Requires predeclaration of all data items to be accessed
     - Uses atomic lock acquisition for all items
     - May implement lock request sorting to prevent circular waits
     - Often uses a global lock manager for coordination
  - **Practical Applications**:
     - Used in systems where predictable performance is more important than maximum concurrency
     - Suitable for transactions with well-defined access patterns
     - Implemented in some real-time database systems

- TimeStamp based Deadlock detection:
  - Old TimeStamp of Txn = High Priority of the Txn
  - Wait-Die:
     - Old txn waits for the New txn
     - ts(T1) < ts(T2), then T1 will wait for T2 to get completed, otherwiase txn will get aborted.
  - Wound-Wait:
     - Old txn give wound to the new txn and make them aborted
     - ts(T1) < ts(T2), then T2 abort and releases its lock otherwise txn will wait.

  - **Comparison of Wait-Die vs. Wound-Wait**:
     - Wait-Die tends to abort younger transactions more often
     - Wound-Wait tends to abort older transactions less frequently
     - Both ensure freedom from deadlocks
     - Choice depends on workload characteristics and transaction priorities
  - **Implementation Considerations**:
     - Requires maintaining transaction timestamps
     - Must handle timestamp generation in distributed environments
     - Needs careful handling of aborted and restarted transactions
     - May implement backoff strategies for restarted transactions

### **Cascading Aborts Problem**

Cascading aborts occur when the abort of one transaction forces the abort of other dependent transactions that have read data modified by the aborted transaction.

**Example Scenario**:
- Transaction T1 updates data item X
- Transaction T2 reads the updated value of X
- Transaction T1 aborts and must rollback its changes to X
- Transaction T2 must also abort because it read an invalid value of X

**Impact of Cascading Aborts**:
- Wasted work as multiple transactions are rolled back
- Reduced system throughput
- Unpredictable performance
- Complex recovery procedures

### **Cascading Aborts Prevention Strategy:**

- Strong Strict 2PL (also know as Rigorous 2PL):
  - Txn is not allowed to acquire or upgrade more lock after growing phase.
  - Release all the locks at the end of the txn only.
  - Cons of strict 2PL
    - Less concurrency
    - Deadlock
  - **How It Prevents Cascading Aborts**:
    - By holding all locks until commit/abort, no transaction can read uncommitted data
    - Ensures transactions only see committed data
    - Creates a commit order that matches the serialization order
    - Provides recoverability without cascading aborts
  - **Implementation Details**:
    - Simplifies implementation of the lock manager
    - Reduces complexity of recovery procedures
    - Often the default in commercial database systems
    - Can be optimized with early lock release for read-only transactions

### **2PL Variants Comparison**

| Variant | Lock Release | Deadlock Prevention | Cascading Aborts | Concurrency Level |
|---------|--------------|---------------------|------------------|-------------------|
| Basic 2PL | After shrinking phase begins | No | Possible | Higher |
| Conservative 2PL | After transaction completes | Yes | Possible | Lower |
| Strict 2PL | Only after transaction completes | No | No | Medium |
| Strong Strict 2PL | Only after transaction completes | No | No | Medium |

### **2PL in Distributed Systems**

- **Challenges**:
  - Coordinating lock management across multiple nodes
  - Higher communication overhead for lock requests
  - Increased latency for lock acquisition
  - More complex deadlock detection and resolution

- **Implementation Approaches**:
  - Centralized lock manager
  - Distributed lock managers with coordination
  - Primary copy approach for each data item
  - Partitioned data with local lock management

- **Integration with Distributed Transactions**:
  - Often combined with Two-Phase Commit (2PC) protocol
  - Lock acquisition during prepare phase
  - Lock release after global commit/abort
  - Requires careful handling of coordinator failures

### **Real-World Applications**

- **Traditional Database Systems**:
  - Most commercial RDBMS implement some form of 2PL
  - Often use Strong Strict 2PL for ACID compliance
  - May offer different isolation levels as performance options

- **Distributed Databases**:
  - Google Spanner combines 2PL with other techniques
  - Distributed SQL databases like CockroachDB use variants of 2PL
  - NoSQL systems may implement simplified versions for specific operations

- **In-Memory Databases**:
  - May use optimized versions of 2PL
  - Often combine with MVCC for better read performance
  - Can implement specialized lock management for higher throughput
