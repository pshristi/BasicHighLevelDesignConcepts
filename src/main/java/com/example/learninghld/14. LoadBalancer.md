## **Load Balancers in System Architecture**

### **What is a Load Balancer?**

A load balancer is a device or software that distributes network traffic across multiple servers to ensure no single server bears too much demand. By spreading the workload, load balancers improve application availability, scalability, and reliability.

### **Why Load Balancers are Important**

1. **High Availability**: Ensures service remains available even if some servers fail
2. **Scalability**: Allows adding more servers to handle increased traffic
3. **Reliability**: Prevents overloading individual servers
4. **Performance**: Reduces response time by distributing load efficiently
5. **Maintenance**: Enables rolling updates without downtime
6. **Security**: Can provide protection against certain types of attacks

### **Load Balancer Architecture**

1. **Physical Placement**:
   - **Edge Load Balancers**: First point of contact for client requests
   - **Internal Load Balancers**: Distribute traffic between internal services
   - **Global Load Balancers**: Route traffic across multiple data centers

2. **Deployment Models**:
   - **Hardware Load Balancers**: Dedicated physical appliances
   - **Software Load Balancers**: Applications running on standard servers
   - **Cloud Load Balancers**: Managed services provided by cloud providers
   - **Virtual Appliances**: Software versions of hardware load balancers

3. **High Availability Configurations**:
   - **Active-Passive**: Standby load balancer takes over if primary fails
   - **Active-Active**: Multiple load balancers share traffic
   - **N+1 Redundancy**: Extra load balancer(s) for failover

### **Types**

- Application load balancer (L7 Balancer)
 : Can read and cache application layer info eg header, data, session info to route traffic
 - **Additional L7 Features**:
   - **Content-Based Routing**: Route based on URL path, headers, or content
   - **SSL Termination**: Handle HTTPS encryption/decryption
   - **Session Persistence**: Ensure user sessions stay on the same server
   - **Application Firewalling**: Filter malicious traffic
   - **HTTP/2 Support**: Optimize modern web traffic
   - **Examples**: NGINX, HAProxy, F5 BIG-IP, AWS ALB

- Network load balancer (L4 Balancer)
  : Can read network layer info eg tcp/udp port, ip address to route traffic
  - **Additional L4 Features**:
    - **Protocol Support**: Handle any TCP/UDP traffic
    - **High Performance**: Lower overhead than L7 balancers
    - **Direct Server Return**: Allow response traffic to bypass the load balancer
    - **NAT**: Network Address Translation capabilities
    - **Examples**: AWS NLB, Google Cloud Network Load Balancer, HAProxy in TCP mode

### **Load Balancer Algorithms**

- Static Load Balancing Algorithms
  - Round Robin
  - Weighted round robin
  - IP Hash
- Dynamic Load Balancing Algorithms
  - Least connection
  - Weighted least connection
  - Least response time

**Additional Algorithms**:
- **Resource-Based**: Distributes load based on server resource utilization (CPU, memory)
- **Random**: Randomly selects a server for each request
- **URL Hash**: Routes based on hashed URL values
- **Least Bandwidth**: Selects server currently serving the least amount of traffic
- **Least Packets**: Selects server that has received the fewest packets
- **Custom Metrics**: Routes based on application-specific metrics

### **Round Robin**

- Advantages: 
  - Very Easy to Implement.
  - Equal load distribution to all the servers. 
- Disadvantages:
  - One Server with high Capacity and Another with Low, both will be treated as same.
  - Chance that Low capacity Server will go down because of overload of requests.
- **Implementation Details**:
  - Maintains a list of servers and a pointer to the current server
  - Advances the pointer sequentially after each request
  - Wraps around to the beginning when it reaches the end
  - Suitable for homogeneous server environments

### **Weighted round robin**

- Advantages:
  - Low Capacity Server, will get saved from receiving the large no of requests.
  - Easy to implement as Weights are static, no dynamic computation.
- Disadvantages:
  - If requests have different processing time, then its possible that Low capacity server get high processing requests and get overburdened.
- **Implementation Details**:
  - Assigns a weight value to each server based on capacity
  - Servers with higher weights receive proportionally more requests
  - Example: Server A (weight 5), Server B (weight 2), Server C (weight 1)
  - Request distribution: A:B:C = 5:2:1
  - Useful for heterogeneous environments with different server capacities

### **IP Hash**

- Advantages:
  - Good for use cases, where Same Client need to connect to Same Server.
  - Easy to implement.
- Disadvantages:
  - If Clients request is coming through PROXY, then all the clients will have same source IP address, and this will OVERLOAD one server.
  - Can not ensure equal distribution.
- **Implementation Details**:
  - Calculates a hash value from the client's IP address
  - Uses the hash to determine which server receives the request
  - Ensures the same client always reaches the same server (session stickiness)
  - Can be combined with weights for better distribution
  - Useful for applications requiring session persistence without cookies

### **Least connection**

- Advantages:
  - Dynamic, as it consider the Load on each server, so chance of Overburdened of the server is less when each server has equal capacity.
- Disadvantages:
  - TCP connections can be ACTIVE but possible have no traffic. So purpose is failed.
  - No Difference between Low Capacity and High Capacity Server. Chance that Low capacity server will get over burdened.
- **Implementation Details**:
  - Tracks the number of active connections to each server
  - Routes new requests to the server with the fewest active connections
  - Requires real-time connection tracking
  - Better suited for long-lived connections
  - Adapts to varying connection durations

### **Weighted Least Connection**

- **Description**: Combines least connections with server weighting
- **Advantages**:
  - Accounts for different server capacities
  - Adapts to current server load
  - Prevents overloading smaller servers
- **Disadvantages**:
  - More complex to implement
  - Requires manual weight configuration
  - May not account for connection complexity
- **Implementation Details**:
  - Divides the current connection count by the server's weight
  - Routes to the server with the lowest ratio
  - Formula: connections ÷ weight = load metric

### **Least response time**

- **Description**: Routes requests to the server with the lowest response time
- **Advantages**:
  - Accounts for actual server performance
  - Adapts to varying request complexity
  - Detects performance degradation automatically
- **Disadvantages**:
  - Requires active health checks
  - More overhead for monitoring
  - Can be affected by network latency
- **Implementation Details**:
  - Monitors response time for health check requests
  - May also consider active connection count
  - Combines response time and connection count for better decisions
  - Well-suited for performance-sensitive applications

### **Health Checking**

Health checks are crucial for load balancers to detect server failures:

1. **Types of Health Checks**:
   - **Passive**: Monitor actual client traffic for failures
   - **Active**: Send dedicated probe requests to verify server health
   - **TCP Checks**: Verify TCP connection establishment
   - **HTTP Checks**: Verify HTTP response codes and content
   - **Custom Checks**: Application-specific health verification

2. **Health Check Configuration**:
   - **Interval**: How frequently checks are performed
   - **Timeout**: Maximum time to wait for a response
   - **Threshold**: Number of consecutive successes/failures to change status
   - **Path**: Specific URL to check for HTTP health checks
   - **Expected Response**: What constitutes a healthy response

3. **Failure Handling**:
   - **Circuit Breaking**: Temporarily remove unhealthy servers
   - **Slow Start**: Gradually increase traffic to recovered servers
   - **Fallback Mechanisms**: Default routes when all servers are unhealthy

### **Session Persistence**

Methods to ensure a client's requests are routed to the same server:

1. **Cookie-Based**:
   - **Insert Mode**: Load balancer inserts a cookie
   - **Prefix Mode**: Load balancer adds prefix to application cookies
   - **Rewrite Mode**: Load balancer modifies existing cookies

2. **IP-Based**:
   - Uses client IP address to determine server
   - Can use IP hash or other consistent hashing algorithms

3. **SSL Session ID**:
   - Routes based on SSL session identifier
   - Useful for HTTPS traffic without terminating SSL

4. **Application-Controlled**:
   - Application determines session affinity
   - Can use distributed session storage

### **SSL/TLS Handling**

Load balancers often manage SSL/TLS encryption:

1. **SSL Termination**:
   - Decrypt at load balancer, forward unencrypted to servers
   - Reduces server CPU load
   - Enables content inspection

2. **SSL Passthrough**:
   - Pass encrypted traffic directly to servers
   - Servers handle decryption
   - Better for regulatory compliance

3. **SSL Bridging**:
   - Decrypt at load balancer, re-encrypt to servers
   - Enables inspection while maintaining encryption

4. **Certificate Management**:
   - Centralized SSL certificate deployment
   - SNI (Server Name Indication) support
   - Certificate rotation and renewal

### **Implementation Considerations**

1. **Performance Factors**:
   - **Throughput**: Maximum traffic volume
   - **Concurrent Connections**: Maximum simultaneous connections
   - **Latency**: Added delay from load balancing
   - **SSL Handling Capacity**: Encryption/decryption performance

2. **Scalability**:
   - **Horizontal Scaling**: Adding more load balancer instances
   - **Vertical Scaling**: Increasing resources for load balancers
   - **Stateless Design**: Enabling easier scaling

3. **Monitoring and Observability**:
   - **Traffic Metrics**: Requests per second, bandwidth
   - **Health Status**: Server availability
   - **Performance Metrics**: Latency, error rates
   - **Connection Stats**: Active and idle connections

4. **Security Considerations**:
   - **DDoS Protection**: Mitigating distributed denial of service attacks
   - **WAF Integration**: Web application firewall capabilities
   - **Rate Limiting**: Preventing abuse
   - **Access Control**: IP-based restrictions

### **Cloud Load Balancing Services**

1. **AWS**:
   - **Application Load Balancer (ALB)**: HTTP/HTTPS traffic
   - **Network Load Balancer (NLB)**: TCP/UDP traffic
   - **Classic Load Balancer**: Legacy option
   - **Global Accelerator**: Global load balancing

2. **Google Cloud**:
   - **HTTP(S) Load Balancing**: Global L7 balancing
   - **Network Load Balancing**: Regional L4 balancing
   - **Internal Load Balancing**: For internal services

3. **Azure**:
   - **Application Gateway**: HTTP load balancing with WAF
   - **Load Balancer**: TCP/UDP load balancing
   - **Traffic Manager**: DNS-based global routing
   - **Front Door**: Global HTTP(S) load balancing

### **Best Practices**

1. **Design for Failure**:
   - Implement redundant load balancers
   - Configure proper health checks
   - Plan for disaster recovery

2. **Performance Optimization**:
   - Choose appropriate algorithm for your workload
   - Configure connection timeouts appropriately
   - Consider SSL offloading for HTTPS traffic

3. **Security Hardening**:
   - Keep load balancer software updated
   - Implement proper access controls
   - Configure appropriate TLS settings
   - Enable logging for security monitoring

4. **Operational Excellence**:
   - Automate load balancer configuration
   - Implement proper monitoring and alerting
   - Document load balancing architecture
   - Test failover scenarios regularly
