## Design a Rate Limiter

### **Why Required ?**
- To prevent DDOS attack 
- To protect APIs from excessive use
- To prevent resource starvation
- To reduce costs by limiting API usage
- To maintain service quality and availability
- To enforce usage quotas for different service tiers

### **What is a Rate Limiter?**

A rate limiter is a tool that monitors the number of requests a client can send to an API within a time window. If the request count exceeds the threshold defined by the rate limiter, all excess calls are blocked.

### **Where to Place Rate Limiters?**

Rate limiters can be implemented at different levels:
- **Client-side**: Limits requests before they're sent (less common)
- **Server-side**: Implemented at the API server level
- **Middleware**: Implemented in API gateways or reverse proxies
- **Database level**: Protects database from excessive queries

### **It has 5 Algorithms:**

- Token Bucket Algorithm
- Leaking Bucket Algorithm
- Fixed Window Counter Algorithm
- Sliding Window Logs Algorithm
- Sliding Window Counter Algorithm

### **Token Bucket Algorithm**

- We have a bucket with limited capacity to hold tokens which gets refilled after defined interval.
- Can be implemented using Redis but atomicity is the concern
- U1 : 11::00::01-3 (timestamp-counter)
![img.png](../../../../resources/img.png)

**How it works:**
1. A token bucket contains tokens, added at a fixed rate (token refill rate)
2. Each request consumes one or more tokens
3. If the bucket has enough tokens, the request is allowed
4. If not enough tokens, the request is either rejected or delayed

**Advantages:**
- Allows for bursts of traffic (up to bucket capacity)
- Simple to implement and understand
- Memory efficient
- Can handle different request costs by consuming different numbers of tokens

**Disadvantages:**
- Requires careful tuning of bucket size and refill rate
- Can still allow uneven traffic patterns

**Use cases:**
- API rate limiting
- Network traffic shaping
- Cloud service request throttling (e.g., AWS API Gateway)

**Implementation example (pseudocode):**
```
function allowRequest(userId, tokensNeeded):
    currentTime = getCurrentTime()
    bucket = getBucket(userId)

    // If bucket doesn't exist, create it
    if bucket == null:
        bucket = {
            tokens: MAX_BUCKET_SIZE,
            lastRefillTimestamp: currentTime
        }

    // Calculate tokens to add based on time elapsed
    timeElapsed = currentTime - bucket.lastRefillTimestamp
    tokensToAdd = timeElapsed * REFILL_RATE

    // Refill bucket
    bucket.tokens = min(MAX_BUCKET_SIZE, bucket.tokens + tokensToAdd)
    bucket.lastRefillTimestamp = currentTime

    // Check if enough tokens and consume them
    if bucket.tokens >= tokensNeeded:
        bucket.tokens -= tokensNeeded
        saveBucket(userId, bucket)
        return true

    saveBucket(userId, bucket)
    return false
```

### **Leaking Bucket Algorithm**

- Implemented using FIFO whose out will be at a predefined interval
![img_1.png](../../../../resources/img_1.png)

**How it works:**
1. Requests enter a FIFO queue (the "bucket")
2. Requests are processed at a fixed rate
3. If the queue is full, new requests are rejected
4. The bucket "leaks" (processes) requests at a constant rate

**Advantages:**
- Provides a consistent outflow rate, smoothing out bursts
- Simple to implement using a queue
- Good for scenarios requiring a steady processing rate

**Disadvantages:**
- No allowance for bursts of traffic
- Can lead to unnecessary request delays
- Fixed processing rate may not be ideal for all scenarios

**Use cases:**
- Network traffic shaping
- Scenarios where consistent processing rate is important
- Systems with limited processing capacity

**Implementation example (pseudocode):**
```
class LeakingBucket:
    constructor(capacity, leakRate):
        this.queue = new Queue(capacity)
        this.leakRate = leakRate  // requests per second
        this.lastLeakTime = getCurrentTime()

    allowRequest(request):
        currentTime = getCurrentTime()

        // Leak requests based on time elapsed
        timeElapsed = currentTime - this.lastLeakTime
        requestsToLeak = floor(timeElapsed * this.leakRate)

        // Remove leaked requests from queue
        for i from 1 to requestsToLeak:
            if not this.queue.isEmpty():
                this.queue.dequeue()

        this.lastLeakTime = currentTime

        // Try to add new request
        if this.queue.isFull():
            return false

        this.queue.enqueue(request)
        return true
```

### **Fixed Window Counter Algorithm**

- Implemented using Redis
- U1-11::00 (user-minute) : 3 (counter)
- U1-11::01 (uset-nextMinute) : 0 (counter)
![img_2.png](../../../../resources/img_2.png)

**How it works:**
1. Time is divided into fixed windows (e.g., 1-minute intervals)
2. Each window has a counter that tracks the number of requests
3. When a new request arrives, the counter for the current window is incremented
4. If the counter exceeds the limit, the request is rejected
5. When a new window starts, the counter resets to zero

**Advantages:**
- Very simple to understand and implement
- Low memory footprint
- Works well for many common rate limiting scenarios

**Disadvantages:**
- Can allow twice the rate limit at window boundaries
  - Example: If limit is 100 requests/minute, a user could make 100 requests at 11:59:59 and another 100 at 12:00:01
- Doesn't account for request distribution within the window

**Use cases:**
- Simple API rate limiting
- User action throttling (e.g., login attempts)
- Basic DDoS protection

**Implementation example (pseudocode):**
```
function allowRequest(userId):
    currentTime = getCurrentTime()
    windowStart = floor(currentTime / WINDOW_SIZE_MS) * WINDOW_SIZE_MS
    key = userId + ":" + windowStart

    counter = getCounter(key)
    if counter == null:
        // First request in this window
        setCounter(key, 1, WINDOW_SIZE_MS)  // Set expiry to window size
        return true

    if counter >= MAX_REQUESTS:
        return false

    incrementCounter(key)
    return true
```

### **Sliding Window Logs Algorithm**

- Can be implemented using hash table/redis
- Not m/o efficient
![img_3.png](../../../../resources/img_3.png)

**How it works:**
1. Store a timestamp for each request in a time-ordered log
2. When a new request arrives, remove all timestamps older than the window
3. Count the remaining timestamps
4. If the count is less than the limit, allow the request and add its timestamp
5. Otherwise, reject the request

**Advantages:**
- Provides perfect rate limiting with no boundary conditions
- Accounts for the exact timing of each request
- Handles uneven traffic patterns well

**Disadvantages:**
- High memory usage (stores every request timestamp)
- Potentially expensive to maintain and clean up old timestamps
- More complex to implement

**Use cases:**
- Precise rate limiting requirements
- Systems where memory usage is not a concern
- Low to moderate traffic scenarios

**Implementation example (pseudocode):**
```
function allowRequest(userId):
    currentTime = getCurrentTime()
    windowStart = currentTime - WINDOW_SIZE_MS

    // Get the log of request timestamps for this user
    requestLog = getRequestLog(userId)

    // Remove timestamps outside the current window
    while requestLog.isNotEmpty() and requestLog.oldest() < windowStart:
        requestLog.removeOldest()

    // Check if we're still within the rate limit
    if requestLog.size() >= MAX_REQUESTS:
        return false

    // Add current request timestamp
    requestLog.add(currentTime)
    saveRequestLog(userId, requestLog)

    return true
```

### **Sliding Window Counter Algorithm**

![img_4.png](../../../../resources/img_4.png)

**How it works:**
1. Combines the fixed window counter and sliding window logs approaches
2. Keeps track of request count in the current window
3. Also considers a portion of the requests from the previous window
4. The rate is calculated as: 
   `rate = current_window_count + previous_window_count * overlap_percentage`

**Advantages:**
- More accurate than fixed window counter
- More memory efficient than sliding window logs
- Smooths out boundary conditions
- Good balance between accuracy and performance

**Disadvantages:**
- More complex to implement than fixed window
- Less precise than sliding window logs
- Requires storing additional state

**Use cases:**
- General-purpose rate limiting
- Systems with moderate to high traffic
- When memory efficiency and accuracy are both important

**Implementation example (pseudocode):**
```
function allowRequest(userId):
    currentTime = getCurrentTime()
    currentWindowStart = floor(currentTime / WINDOW_SIZE_MS) * WINDOW_SIZE_MS
    previousWindowStart = currentWindowStart - WINDOW_SIZE_MS

    // Get counts for current and previous windows
    currentCount = getCounter(userId + ":" + currentWindowStart) || 0
    previousCount = getCounter(userId + ":" + previousWindowStart) || 0

    // Calculate the overlap percentage of the current request in the rolling window
    elapsedTimeInCurrentWindow = currentTime - currentWindowStart
    windowOverlapPercentage = 1 - (elapsedTimeInCurrentWindow / WINDOW_SIZE_MS)

    // Calculate the rolling count
    rollingCount = currentCount + previousCount * windowOverlapPercentage

    if rollingCount >= MAX_REQUESTS:
        return false

    // Increment the current window counter
    incrementCounter(userId + ":" + currentWindowStart, WINDOW_SIZE_MS * 2)

    return true
```

### **Problems with Rate Limiter**

- **Inconsistency**: Can be solved using sticky session at LB
  - In distributed systems, different rate limiter instances may have different counts
  - Sticky sessions ensure a user's requests always go to the same rate limiter instance
  - Alternative: Use a centralized data store like Redis for counter storage

- **Race condition**: Can be avoided using locks but adds to latency
  - Multiple concurrent requests might all check the counter before any updates it
  - Solutions:
    - Distributed locks (e.g., Redis-based locks)
    - Atomic operations (e.g., Redis INCR command)
    - Optimistic locking with retries

- **Performance overhead**:
  - Rate limiting adds latency to each request
  - Requires additional infrastructure (Redis, etc.)
  - Solutions:
    - Local caching to reduce external calls
    - Batched updates to counters
    - Sampling (only check rate limits for a percentage of requests)

- **Accurate time synchronization**:
  - Time-based algorithms require synchronized clocks across servers
  - Solutions:
    - Use NTP (Network Time Protocol)
    - Centralized timestamp service
    - Time windows with some overlap to account for clock skew

### **Rate Limiter Response Strategies**

When a request exceeds the rate limit, there are several ways to respond:

1. **HTTP 429 (Too Many Requests)**:
   - Return a standard status code with a clear error message
   - Include headers like `Retry-After` to indicate when to try again

2. **Queuing**:
   - Instead of rejecting, queue excess requests for later processing
   - Good for systems where all requests must eventually be processed

3. **Request throttling**:
   - Slow down processing rather than rejecting outright
   - Gradually increase delays as limits are approached

4. **Priority-based processing**:
   - Allow premium users higher rate limits
   - Process higher priority requests first when limits are reached

### **Distributed Rate Limiting Considerations**

For large-scale systems:

1. **Centralized counter store**:
   - Use Redis or similar for storing counters
   - Benefit: Consistent view across all application servers
   - Challenge: Potential bottleneck and single point of failure

2. **Eventual consistency**:
   - Accept that counters might be temporarily inconsistent
   - Periodically synchronize counters between nodes
   - Trade-off accuracy for performance

3. **Sharded rate limiters**:
   - Partition users/clients across multiple rate limiter instances
   - Reduces load on any single instance
   - Requires consistent hashing or similar for routing

### **Conclusion**

Rate limiting is an essential component of robust API design and system architecture. The choice of algorithm depends on your specific requirements:

- **Token Bucket**: Best for allowing occasional bursts while maintaining a long-term rate limit
- **Leaking Bucket**: Ideal for systems requiring a constant outflow rate
- **Fixed Window Counter**: Simplest to implement but has boundary issues
- **Sliding Window Logs**: Most accurate but memory-intensive
- **Sliding Window Counter**: Good balance between accuracy and efficiency

When implementing rate limiting, consider:
- The granularity of limits (per user, per IP, per API key)
- The time window for limits (per second, minute, hour, day)
- How to communicate limits to clients (HTTP headers, documentation)
- How to handle distributed deployment challenges

A well-designed rate limiter not only protects your system from abuse but also ensures fair resource allocation among all users.
