## **OAuth 2.0 (Open Authorization)**

OAuth 2.0 is an industry-standard protocol for authorization that enables applications to obtain limited access to user accounts on an HTTP service.

### **Why OAuth 2.0 is Used**

- Why its used?
  - It's a Authorization framework.
  - Enables secure third-party access to user protected data.
  - **Delegation of Access**: Allows users to grant third-party applications access to their resources without sharing credentials
  - **Standardized Protocol**: Provides a consistent way for applications to request and receive access tokens
  - **Separation of Concerns**: Clearly separates authentication from authorization
  - **Fine-grained Access Control**: Enables limiting access to specific resources through scopes
  - **Wide Adoption**: Supported by major service providers (Google, Facebook, Microsoft, etc.)

### **Real-World Examples**

- **"Login with Google/Facebook"**: Websites using social login
- **Third-Party API Access**: Applications accessing data from services like Twitter, GitHub, or Spotify
- **Mobile App Authorization**: Mobile apps accessing cloud services on behalf of users
- **Microservices Architecture**: Service-to-service authorization within an organization
- **IoT Device Authorization**: Smart devices accessing cloud services

### **Key Concepts**

- **Access Token**: Credential used to access protected resources
- **Refresh Token**: Credential used to obtain new access tokens when they expire
- **Scope**: Permissions that determine what resources the access token can access
- **Consent**: Process where the resource owner approves the requested access
- **State Parameter**: Value used to prevent CSRF attacks during the authorization process

### **OAuth 2.0 Roles**

- Four imp actors/roles involved in it
  - Resource owner
    - **Definition**: The user who owns the protected resources (typically the end-user)
    - **Responsibilities**: Grants or denies permission for the client to access their resources
    - **Example**: A user with a Google account who wants to allow a printing service to access their Google Drive files
  - Client 
    - **Definition**: The application requesting access to protected resources
    - **Responsibilities**: Requests authorization from the resource owner and access tokens from the authorization server
    - **Types**: Confidential clients (can securely store secrets) and public clients (cannot securely store secrets)
    - **Example**: A mobile app, web application, or server-side application
  - Authorization server
    - **Definition**: The server that authenticates the resource owner and issues access tokens
    - **Responsibilities**: Verifies identity, obtains consent, and issues tokens
    - **Components**: Authentication endpoint, token endpoint, and sometimes a token introspection endpoint
    - **Example**: Google's authorization servers for Google APIs
  - Resource hosting server
    - **Definition**: The server hosting the protected resources
    - **Responsibilities**: Validates access tokens and serves protected resources
    - **Security Measures**: Verifies token validity, scope, and expiration
    - **Example**: Google Drive API servers hosting user files

### **Authorization Grant Types**

- Authorization Grant Types : Mechanism used by client to obtain Access Token
  - Authorization Code Grant
  - Implicit Grant
  - Resource Owner Password Credentials Grant
  - Client Credential Grant
  - Refresh Token Grant
  - **Additional Grant Types**:
    - **Device Code Grant**: For devices with limited input capabilities (smart TVs, IoT devices)
    - **Authorization Code Grant with PKCE**: Enhanced security for public clients
    - **JWT Bearer Grant**: Uses JWT assertions to request tokens

### **Authorization Code Grant**

The Authorization Code Grant is the most commonly used and most secure OAuth 2.0 flow, particularly suitable for server-side applications.

![img_1.png](../../../../resources/img_41.png)

- Bearer: is a security mechanism, and it means that client should add the TOKEN in the authorization header, whenever it want to access the protected resources.
- Token Value: it can either be JWT token or plain string.
- Expiry Time: generally its in seconds. After expiry Refresh token should be used to get new Tokens.

**Detailed Flow**:
1. **Client Initiates Flow**: The client redirects the user to the authorization server with client ID, redirect URI, response type ("code"), scope, and state parameter
2. **User Authentication**: The user logs in to the authorization server and grants permissions
3. **Authorization Code Issuance**: The authorization server redirects back to the client with an authorization code
4. **Token Exchange**: The client exchanges the authorization code for an access token by sending a request to the token endpoint with the code, client ID, client secret, and redirect URI
5. **Token Issuance**: The authorization server validates the request and issues access and refresh tokens

**Best Suited For**:
- Web applications with a server-side component
- Native mobile applications (with PKCE enhancement)
- Applications that can securely store client secrets
- Scenarios requiring long-term access through refresh tokens

**Security Advantages**:
- Access tokens are never exposed to the browser or mobile app
- Client authentication provides additional security layer
- Short-lived authorization codes minimize risk if intercepted
- Can implement PKCE (Proof Key for Code Exchange) for additional security

### **Refresh Token Grant**

- Used to get new access token
- **Purpose**: Obtain a new access token when the current one expires without requiring user re-authentication
- **Flow**:
  1. Client sends refresh token to token endpoint with client credentials
  2. Authorization server validates refresh token and client credentials
  3. Authorization server issues new access token (and optionally a new refresh token)
- **Security Considerations**:
  - Refresh tokens should be stored securely
  - Refresh tokens should be rotated periodically
  - Authorization servers should validate client identity before issuing new tokens
  - Refresh tokens should have appropriate expiration policies
- **Implementation Example**:
  ```
  POST /oauth/token HTTP/1.1
  Host: authorization-server.com
  Content-Type: application/x-www-form-urlencoded

  grant_type=refresh_token
  &refresh_token=tGzv3JOkF0XG5Qx2TlKWIA
  &client_id=s6BhdRkqt3
  &client_secret=7Fjfp0ZBr1KtDRbnfVdmIw
  ```

### **Implicit Grant**

- No 2 step process to get access token
- No refresh token returned in this
- **Flow**:
  1. Client redirects user to authorization server with client ID, redirect URI, response type ("token"), scope, and state
  2. User authenticates and grants permissions
  3. Authorization server redirects back to client with access token in the URI fragment
  4. Client extracts token from fragment
- **Best Suited For**:
  - Single-page applications (SPAs)
  - Applications without a server-side component
  - Scenarios where immediate access is needed
- **Security Considerations**:
  - Access tokens are exposed to the browser and potentially to malicious scripts
  - No refresh tokens to limit exposure time
  - Should use short-lived access tokens
  - Being deprecated in favor of Authorization Code Grant with PKCE
- **Limitations**:
  - Cannot securely use refresh tokens
  - Access tokens are visible in browser history
  - Limited token lifetime requires frequent re-authentication

### **Resource Owner Password Credentials Grant**

- Here grant_type is password
- There is no separate Authorization call in ROPC Grant
- Username and Password is not required during refresh token usage
- **Flow**:
  1. User provides username and password directly to the client application
  2. Client sends these credentials to the authorization server along with client credentials
  3. Authorization server validates credentials and issues access and refresh tokens
- **Best Suited For**:
  - First-party applications (developed by the same organization as the authorization server)
  - Migration scenarios from legacy authentication systems
  - Highly trusted applications where redirection flows aren't possible
- **Security Considerations**:
  - Requires high level of trust in the client application
  - Exposes user credentials to the client application
  - Should be used only when other grant types are not viable
  - Not recommended for third-party applications
- **Implementation Example**:
  ```
  POST /oauth/token HTTP/1.1
  Host: authorization-server.com
  Content-Type: application/x-www-form-urlencoded

  grant_type=password
  &username=johndoe
  &password=A3ddj3w
  &client_id=s6BhdRkqt3
  &client_secret=7Fjfp0ZBr1KtDRbnfVdmIw
  ```

### **Client Credential Grant**

- Used when resource owner is same as cliet
- There is no Refresh token required in this.
- There is no Authorization call too.
- **Flow**:
  1. Client sends its credentials to the token endpoint
  2. Authorization server validates client credentials
  3. Authorization server issues an access token
- **Best Suited For**:
  - Machine-to-machine (M2M) communication
  - Microservices accessing other services
  - Backend services performing operations on their own behalf
  - Scenarios where no user context is involved
- **Security Considerations**:
  - Client credentials must be kept secure
  - Access should be limited to necessary resources only
  - Monitoring for unusual access patterns is important
  - Strong client authentication mechanisms should be used
- **Implementation Example**:
  ```
  POST /oauth/token HTTP/1.1
  Host: authorization-server.com
  Content-Type: application/x-www-form-urlencoded

  grant_type=client_credentials
  &client_id=s6BhdRkqt3
  &client_secret=7Fjfp0ZBr1KtDRbnfVdmIw
  ```

### **Token Types and Usage**

- **Bearer Tokens**:
  - Most common token type in OAuth 2.0
  - Possession of the token grants access to protected resources
  - Must be transmitted over HTTPS to prevent interception
  - Included in HTTP requests via Authorization header: `Authorization: Bearer <token>`

- **JWT (JSON Web Tokens)**:
  - Self-contained tokens with encoded claims
  - Can include user information, permissions, and metadata
  - Digitally signed to ensure integrity
  - Can be validated without contacting the authorization server
  - Structure: header.payload.signature

- **Token Security Best Practices**:
  - Store tokens securely (HttpOnly cookies for web apps, secure storage for mobile)
  - Use short expiration times for access tokens
  - Implement token revocation capabilities
  - Validate tokens properly on the resource server
  - Use TLS/SSL for all communications

### **OAuth 2.0 Security Considerations**

- **Common Vulnerabilities**:
  - CSRF (Cross-Site Request Forgery): Mitigated using state parameter
  - Token leakage: Proper storage and transmission of tokens
  - Open redirectors: Validate redirect URIs against whitelist
  - Phishing attacks: Educate users about proper authorization server URLs

- **Security Enhancements**:
  - **PKCE (Proof Key for Code Exchange)**: Protects authorization code flow for public clients
  - **OAuth 2.0 Token Binding**: Cryptographically binds tokens to TLS connections
  - **Mutual TLS Authentication**: Adds certificate-based authentication for clients
  - **JWT Secured Authorization Response Mode (JARM)**: Secures authorization responses

- **Best Practices**:
  - Always use HTTPS for all OAuth endpoints
  - Validate all redirect URIs
  - Implement proper token validation
  - Use appropriate grant types for each use case
  - Keep client secrets secure
  - Implement proper error handling
  - Regularly audit token usage and permissions
