## **Distributed Caching Systems**

### **What is Caching?**

It is technique to store frequently used data in fast access memory so that every time data is needed, we need not to access slow access memory
There are different types of caching present at diff layers of system
- Client side caching (Browser caching)
- CDN (used to store static data)
- Load balancer
- Server side caching (like Redis etc)

**Additional Caching Layers**:
- **CPU Cache**: L1, L2, L3 caches in processors
- **Database Caching**: Buffer pools, query caches
- **Application Caching**: In-memory data structures
- **API Caching**: Caching responses from external APIs
- **DNS Caching**: Storing DNS resolution results

### **Why Caching is Important**

1. **Performance Improvement**: Reduces latency by serving data from faster storage
2. **Scalability**: Reduces load on backend systems
3. **Cost Efficiency**: Decreases resource usage for expensive operations
4. **Availability**: Provides data access even when backend systems are unavailable
5. **User Experience**: Delivers faster response times to end users

### **Distributed caching**

There is cache client associated with each app server which selects cache server from a pool using consistent hashing

**Expanded Definition**:
A distributed cache is a caching system where the cached data is spread across multiple nodes (servers) to provide scalability, reliability, and performance. Unlike a local cache that exists on a single server, a distributed cache allows multiple application servers to share cached data.

### **Distributed Cache Architecture**

1. **Components**:
   - **Cache Clients**: Libraries integrated with application servers
   - **Cache Servers**: Dedicated servers storing cached data
   - **Cluster Manager**: Coordinates cache servers (optional)
   - **Persistence Layer**: For durability (optional)

2. **Topologies**:
   - **Client-Server**: Applications connect to dedicated cache servers
   - **Peer-to-Peer**: Each node acts as both client and server
   - **Master-Slave**: Primary nodes handle writes, replicas handle reads
   - **Sharded**: Data partitioned across multiple nodes

3. **Data Distribution Methods**:
   - **Consistent Hashing**: Minimizes redistribution when nodes change
   - **Range Partitioning**: Divides data based on key ranges
   - **Directory-Based**: Uses a lookup service to locate data

### **Key Features of Distributed Caches**

1. **Elasticity**:
   - Ability to add or remove nodes dynamically
   - Automatic data rebalancing when cluster topology changes

2. **High Availability**:
   - Data replication across multiple nodes
   - Automatic failover when nodes go down
   - No single point of failure

3. **Consistency Models**:
   - **Strong Consistency**: All reads return the most recent write
   - **Eventual Consistency**: All replicas eventually converge
   - **Session Consistency**: Client always sees its own writes

4. **Eviction Policies**:
   - **Least Recently Used (LRU)**: Removes least recently accessed items
   - **Least Frequently Used (LFU)**: Removes least frequently accessed items
   - **Time To Live (TTL)**: Removes items after a specified time
   - **First In First Out (FIFO)**: Removes oldest items first

5. **Data Processing Capabilities**:
   - **Near Cache**: Local cache on client side
   - **Compute Grid**: Execute code where data resides
   - **Event Processing**: React to data changes

### **Popular Distributed Cache Technologies**

1. **Redis**:
   - In-memory data structure store
   - Rich data types (strings, hashes, lists, sets)
   - Pub/sub messaging
   - Lua scripting
   - Persistence options

2. **Memcached**:

3. **Hazelcast**:

4. **Apache Ignite**:
   - In-memory computing platform

5. **Cloud Provider Caching Services**:

   - Google Cloud Memorystore

### **Caching Strategies**

Caching strategies define how data flows between the application, cache, and database. Each strategy has specific use cases and trade-offs.

#### **Cache-Aside Caching Strategy**

Data first read from cache. If present, returned immediately. If not, its fetched from DB, updates the cache and returns

![img.png](../../../../resources/img_14.png)

- Pros
  - Good approach for Heavy Read application.
  -  Even Cache is down, request will not fail, as it will fetch the data from DB.
  - Control over what gets cached. Cache Document data structure can be different than the Data present in DB.
- Cons
  - Without appropriate caching is not used during Write operation. There is a chance of Inconsistency between Cache and DB.
  - For new data read, there will always be CACHE-MISS first. (to resolve this, generally we can pre-heat the cache).

**Additional Details**:
- **Also Known As**: Lazy Loading
- **Implementation Responsibility**: Application code
- **Flow**:
  1. Application checks cache for data
  2. If cache hit, return data
  3. If cache miss, application reads from database
  4. Application updates cache with retrieved data
  5. Application returns data to client
- **Best For**:
  - Read-heavy workloads
  - Data that changes infrequently
  - Applications requiring fine-grained control over caching
- **Real-world Examples**:
  - Web page caching
  - Product catalog caching
  - User profile caching
- **Implementation Considerations**:
  - Set appropriate TTL to manage cache staleness
  - Consider cache stampede protection for popular items
  - Implement proper error handling for cache failures

#### **Read Through Caching Strategy**

Data is read from cache. If present, returned immediately. If not, its fetched from DB by the cache server itself, updated in cache and returned

![img_1.png](../../../../resources/img_15.png)

- Pros
  - Good approach for Heavy Read application.
  - Logic of fetching the data from DB and updating Cache is separated from the application.
- Cons
  - For new data read, there will always be CACHE-MISS first. (to resolve this, generally we can pre-heat the cache)
  - Without appropriate caching is not used during Write operation. There is a chance of Inconsistency between Cache and DB.
  - Cache Document structure should be same as DB table.

**Additional Details**:
- **Implementation Responsibility**: Cache provider/library
- **Flow**:
  1. Application requests data from cache
  2. If cache hit, return data
  3. If cache miss, cache system reads from database
  4. Cache system updates itself with retrieved data
  5. Cache returns data to application
- **Differences from Cache-Aside**:
  - Cache system (not application) is responsible for loading data
  - Application code is simpler
  - Requires cache provider with read-through capability
- **Best For**:
  - Applications where caching logic should be abstracted away
  - Standardized data access patterns
  - When using cache providers with built-in read-through support
- **Real-world Examples**:
  - Enterprise applications with standardized data access
  - Applications using ORM with integrated caching

#### **Write Around Caching Strategy**

Data is written to the DB. Its updated in the cache, only when read operation is performed

![img_2.png](../../../../resources/img_16.png)

- Pros
  - Good approach for Heavy Read application.
  - Resolves Inconsistency problem between Cache and DB.
- Cons
  - For new data read, there will always be CACHE-MISS first. (to resolve this, generally we can pre-heat the cache)
  - If DB is down, Write operation will fail.

**Additional Details**:
- **Implementation Responsibility**: Application code
- **Flow**:
  1. Application writes data directly to database
  2. Cache is not updated during write
  3. Data is loaded into cache only when read (using cache-aside or read-through)
- **Best For**:
  - Write-heavy workloads where data isn't immediately read
  - Log data or time-series data
  - Data that would otherwise flood and churn the cache
- **Real-world Examples**:
  - Logging systems
  - Analytics data collection
  - Infrequently accessed historical data
- **Implementation Considerations**:
  - Consider cache invalidation for related data
  - May need to implement cache warming for critical data

#### **Write Through Caching Strategy**

Data is written to the DB and cache in same transaction making sure Cache is always consistent with the DB

![img_3.png](../../../../resources/img_17.png)

- Pros
  - Cache and DB always remain consistent.
  - Cache Hit chance increases a lot.
- Cons
  - Alone its not useful, it will increase the latency. (that's why its always used with Read through or cache aside cache)
  - 2 Phase commit, need to be supported with this. To maintain the transactional property.
  - If DB is down, write operation will fail.

**Additional Details**:
- **Implementation Responsibility**: Cache provider/library or application
- **Flow**:
  1. Application writes data to cache
  2. Cache immediately writes data to database (synchronously)
  3. Write operation completes only after both cache and database are updated
- **Best For**:
  - Applications requiring data consistency
  - Systems where reads happen shortly after writes
  - When combined with read-through or cache-aside for reads
- **Real-world Examples**:
  - Financial data caching
  - Inventory management systems
  - User session data
- **Implementation Considerations**:
  - Increases write latency
  - Consider distributed transaction management
  - Plan for failure scenarios in either cache or database

#### **Write Back Caching Strategy**

Data is written to Cache and read from Cache. Its updated in DB asynchronously using a queue/scheduler

![img_4.png](../../../../resources/img_18.png)

- Pros: 
  - Good for Write heavy application
  - Cache Hit chance increases a lot.
  - Improves the Write operation Latency. As writing into the DB happens asynchronously.
  - Gives much better performance when used with read through cache.
  - Even when DB fails, Write operation will still works.
- Cons:
  - If Data is removed from Cache and DB write still not happens, then there is a chance of an issue. (it is handled by keeping the TAT of cache little higher like 2 days)

**Additional Details**:
- **Also Known As**: Write-Behind or Write-Deferred
- **Implementation Responsibility**: Cache provider/library or application
- **Flow**:
  1. Application writes data to cache
  2. Write operation completes immediately
  3. Cache asynchronously writes data to database
  4. Batching of writes may occur for efficiency
- **Best For**:
  - Write-intensive workloads
  - Systems that can tolerate some data loss
  - Applications where write performance is critical
- **Real-world Examples**:
  - High-volume data collection systems
  - Gaming leaderboards
  - Social media activity feeds
- **Implementation Considerations**:
  - Implement reliable queue/persistence for pending writes
  - Plan for failure recovery
  - Consider write coalescing for frequently updated items

### **Hybrid Caching Strategies**

In practice, many systems combine multiple caching strategies:

1. **Read-Through + Write-Through**:
   - Consistent reads and writes
   - Higher write latency but guaranteed consistency
   - Good for systems requiring strong consistency

2. **Cache-Aside + Write-Behind**:
   - Application-controlled reads with high-performance writes
   - Good for systems with complex read logic but high write volume
   - Requires careful implementation to handle edge cases

3. **Read-Through + Write-Around + Periodic Refresh**:
   - Efficient writes with controlled cache freshness
   - Background processes refresh cache periodically
   - Good for systems with predictable access patterns

### **Cache Consistency Challenges**

1. **Cache Invalidation**:
   - **Time-Based**: Items expire after TTL
   - **Event-Based**: Cache updated/invalidated when data changes
   - **Explicit**: Application manually invalidates entries
   - **Version-Based**: Cache entries include version information

2. **Consistency Patterns**:
   - **Strong Consistency**: Cache always reflects latest data (expensive)
   - **Eventual Consistency**: Cache may temporarily have stale data
   - **Read-Your-Writes Consistency**: Users always see their own updates

3. **Common Issues**:
   - **Thundering Herd**: Many simultaneous cache misses for same key
   - **Cache Penetration**: Requests for non-existent keys bypass cache
   - **Cache Avalanche**: Mass expiration causing database overload
   - **Cache Pollution**: Low-value data displacing high-value data

### **Implementation Best Practices**

1. **Cache Key Design**:
   - Use consistent naming conventions
   - Include version or type information
   - Consider key length limitations
   - Avoid characters that need escaping

2. **Data Serialization**:
   - Choose efficient serialization format (JSON, Protocol Buffers, etc.)
   - Consider compression for large values
   - Handle serialization errors gracefully

3. **Cache Sizing**:
   - Calculate working set size
   - Monitor cache hit rates
   - Plan for growth
   - Consider memory overhead of cache metadata

4. **Monitoring and Observability**:
   - Track hit/miss ratios
   - Monitor eviction rates
   - Measure latency impact
   - Set alerts for cache failures

5. **Resilience Patterns**:
   - Implement circuit breakers for cache failures
   - Use timeouts for cache operations
   - Consider fallback strategies
   - Test cache failure scenarios

6. **Security Considerations**:
   - Encrypt sensitive cached data
   - Implement access controls
   - Consider cache poisoning attacks
   - Sanitize data before caching
