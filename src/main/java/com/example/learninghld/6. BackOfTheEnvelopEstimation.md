## Back of the Envelope Estimation

Back of envelope calculations is a technique used within software engineering to determine how a system should be designed. The method is often expected in system design interviews too.

Sometimes we face a choice between alternative design or architecture. At interviewer can ask if a single server is sufficient? If not, how many servers would we need? or do we need cache? what is Memory Capacity you need?  A quick calculation gives us a rough estimate.

### Why Back-of-the-Envelope Calculations Matter

- **Feasibility Assessment**: Quickly determine if an approach is viable before detailed design
- **Resource Planning**: Estimate hardware requirements early in the design process
- **Bottleneck Identification**: Identify potential system bottlenecks before implementation
- **Cost Estimation**: Approximate infrastructure costs for budgeting
- **Interview Success**: Demonstrate systematic thinking and practical knowledge in system design interviews

### What to Estimate

As part of the estimation, i compute 3 things:
1. Estimate Number of Servers Required.
2. RAM Memory estimate number
3. Storage capacity estimate number

Additional estimations often include:
- Network bandwidth requirements
- Database QPS (Queries Per Second)
- Cache size and hit ratio
- CDN capacity
- Load balancer throughput

### Estimation Process

1. **Clarify Requirements**
   - Understand the scale (users, requests, data volume)
   - Define the scope (features, functionality)
   - Establish constraints (latency, availability)

2. **Make Reasonable Assumptions**
   - Daily active users (DAU)
   - Usage patterns (reads vs. writes)
   - Data size per entity
   - Request distribution (peak vs. average)

3. **Calculate Core Metrics**
   - QPS (Queries Per Second) = DAU × actions per day ÷ seconds in a day
   - Storage = number of entities × size per entity
   - Memory = active dataset size + caching needs

4. **Apply Safety Factors**
   - Add 30-50% buffer for growth
   - Consider peak traffic (2-3× average)
   - Account for data replication (2-3× for redundancy)

### Common Estimation Examples

**Example 1: Twitter-like Service**
- 200M DAU, each user posts 2 tweets/day and reads 200 tweets/day
- QPS calculation:
  - Write QPS: 200M × 2 ÷ 86400 ≈ 4,630 writes/sec
  - Read QPS: 200M × 200 ÷ 86400 ≈ 463,000 reads/sec
  - Peak QPS: 463,000 × 2 ≈ 926,000 QPS (assuming 2× peak factor)

**Example 2: Photo Sharing App**
- 100M users, each uploads 2 photos/day, average photo size 200KB
- Storage calculation:
  - Daily new storage: 100M × 2 × 200KB = 40TB/day
  - Annual storage: 40TB × 365 = 14.6PB/year

**Example 3: Video Streaming Service**
- 50M users, each watches 1 hour/day, streaming at 1MB/sec
- Bandwidth calculation:
  - Average bandwidth: 50M × 1MB/sec × (percentage watching simultaneously)
  - If 10% concurrent users: 50M × 0.1 × 1MB/sec = 5,000,000 MB/sec = 5TB/sec

**Cheat Sheet**

            | Traffic       | Storage

### Additional Reference Values

**Traffic Estimates**
- 1 request per second = ~2.5 million requests per month
- 40 requests per second = ~100 million requests per month
- 400 requests per second = ~1 billion requests per month

**Latency Numbers**
- Memory access: ~100 ns
- SSD random read: ~100 μs (1,000× slower than memory)
- Network roundtrip within same region: ~1 ms
- HDD seek: ~10 ms
- Network roundtrip US to Europe: ~100 ms

**Server Capabilities (Approximate)**
- Modern web server: 10,000-50,000 QPS per core
- Database QPS: 1,000-10,000 QPS per instance (varies widely)
- Network throughput: 1-10 Gbps per server
- RAM: 64-256 GB per server
- SSD: 1-4 TB per server

### Tips for System Design Interviews

1. **Start with user requirements**
   - "Let's assume we have X million DAU..."
   - "If each user performs Y actions per day..."

2. **Show your work**
   - Write down assumptions and calculations
   - Round numbers for simplicity

3. **Sanity check your results**
   - "This seems high/low, let me double-check..."
   - Compare with known systems

4. **Discuss trade-offs**
   - "We could reduce storage by compressing data, but that would increase CPU usage..."

5. **Be prepared to adjust**
   - "If the requirement changes to handle 10× more traffic, we would need to..."
