## **Designing High Availability and Resilient Systems**

### **What is High Availability?**

High Availability (HA) refers to a system's ability to remain operational and accessible for extended periods of time. The goal is to minimize downtime and ensure continuous operation, typically measured as a percentage of uptime (e.g., 99.99% or "four nines").

### **What is Resilience?**

Resilience is a system's ability to handle and recover from failures. While high availability focuses on preventing downtime, resilience focuses on how well a system responds to and recovers from failures when they do occur.

### **Why Are They Important?**

1. **Business Continuity**: Prevents revenue loss due to system downtime
2. **User Trust**: Maintains user confidence in the reliability of your service
3. **SLA Compliance**: Helps meet Service Level Agreements with customers
4. **Competitive Advantage**: Differentiates your service from less reliable alternatives
5. **Disaster Recovery**: Enables quick recovery from catastrophic failures

### **Key Concepts and Metrics**

1. **Availability Percentage**: Calculated as (Uptime / Total Time) × 100%
   - 99% ("two nines") = 87.6 hours of downtime per year
   - 99.9% ("three nines") = 8.76 hours of downtime per year
   - 99.99% ("four nines") = 52.56 minutes of downtime per year
   - 99.999% ("five nines") = 5.26 minutes of downtime per year

2. **Mean Time Between Failures (MTBF)**: Average time between system failures

3. **Mean Time To Recovery (MTTR)**: Average time to restore service after a failure

4. **Recovery Point Objective (RPO)**: Maximum acceptable data loss measured in time

5. **Recovery Time Objective (RTO)**: Maximum acceptable time to restore service

### **Common Failure Points**

1. **Hardware Failures**: Server crashes, disk failures, network equipment failures
2. **Software Failures**: Bugs, memory leaks, resource exhaustion
3. **Network Issues**: Connectivity problems, DNS failures, routing issues
4. **Power Outages**: Loss of electricity to data centers
5. **Human Error**: Misconfigurations, accidental deletions, deployment errors
6. **External Dependencies**: Third-party service outages, API failures
7. **Security Incidents**: DDoS attacks, breaches, ransomware

### **Architecture Patterns for High Availability**

#### **Active Passive Architecture**

- Only one master node and others are replica. We can configure to redirects all R and RW requests to Master DB or to redirect RW to master and R to replicas
- Undirectional sync will happen from master to replica
- Replica will serve as master incase of master failure
- MySQL db
- **Additional Details**:
  - Also known as Primary-Secondary or Master-Slave architecture
  - Failover process can be automatic or manual
  - Lower cost but potential downtime during failover
  - Simpler to implement and maintain
  - Examples: Traditional MySQL replication, PostgreSQL streaming replication
  - **Failover Process**:
    1. Heartbeat monitoring detects primary node failure
    2. Secondary node is promoted to primary
    3. DNS or load balancer configuration is updated
    4. Clients reconnect to the new primary

#### **Active Active Architecture**

- Multi master nodes can co-exists. 
- Bidirectional sync will happen from multi masters which is the most complex thing here
- NoSql db
- **Additional Details**:
  - Also known as Multi-Master or Master-Master architecture
  - All nodes can accept read and write operations simultaneously
  - Higher cost but minimal or no downtime during node failures
  - More complex to implement and maintain
  - In distributed databases or systems (like DynamoDB, Cassandra), multiple replicas can independently update the same data — especially in eventual consistency setups. This can lead to conflicts.
    - Vector Clocks: A vector clock is a tool that tracks causality between events across nodes in a distributed system.
      - Eg [ A:2, B:1, C:0 ]
    - Each time a node updates data, it increments its own clock.
  - Requires conflict resolution strategies
  - Examples: Cassandra, CouchDB, MySQL with Group Replication
  - **Conflict Resolution Strategies**:
    - Last-write-wins (based on timestamps)
    - Vector clocks (tracking causal relationships)
    - Custom conflict resolution logic

### **Redundancy Strategies**

1. **Geographic Redundancy**:
   - Distributing systems across multiple physical locations
   - Protects against regional disasters, power outages, network issues
   - Requires data replication and synchronization
   - Examples: Multi-region cloud deployments, globally distributed databases

2. **Component Redundancy**:
   - Duplicating critical components within a system
   - Eliminates single points of failure
   - Examples: Redundant power supplies, RAID storage, clustered servers

3. **Network Redundancy**:
   - Multiple network paths and providers
   - BGP routing for automatic failover
   - Examples: Dual ISP connections, redundant network equipment

4. **Data Redundancy**:
   - Multiple copies of data stored in different locations
   - Synchronous vs. asynchronous replication
   - Examples: Database replication, distributed file systems, backups

### **Load Balancing for High Availability**

1. **Types of Load Balancers**:
   - Hardware load balancers (F5, Citrix)
   - Software load balancers (NGINX, HAProxy)
   - DNS-based load balancing
   - Cloud load balancing services (AWS ELB, Google Cloud Load Balancing)

2. **Load Balancing Algorithms**:
   - Round Robin: Distributes requests sequentially
   - Least Connections: Sends requests to servers with fewest active connections
   - IP Hash: Uses client IP to determine server (helps with session persistence)
   - Weighted: Assigns different capacities to different servers

3. **Health Checks**:
   - Active monitoring of backend servers
   - Automatic removal of unhealthy servers from rotation
   - Periodic checks via HTTP, TCP, or custom protocols

### **Fault Tolerance Techniques**

1. **Circuit Breakers**:
   - Prevents cascading failures by failing fast
   - Automatically stops calls to failing services
   - Gradually tests recovery before resuming normal operation
   - Examples: Netflix Hystrix, Resilience4j

2. **Bulkheads**:
   - Isolates components to contain failures
   - Separate thread pools, connection pools, or services
   - Prevents one failing component from consuming all resources

3. **Timeouts and Retries**:
   - Setting appropriate timeouts for all external calls
   - Implementing exponential backoff for retries
   - Using jitter to prevent thundering herd problems

4. **Graceful Degradation**:
   - Providing reduced functionality instead of complete failure
   - Fallback mechanisms for critical features
   - Example: Serving cached content when database is unavailable

### **Monitoring and Alerting**

1. **Key Metrics to Monitor**:
   - System health: CPU, memory, disk, network
   - Application metrics: Response times, error rates, throughput
   - Business metrics: Transactions, user activity, revenue
   - Dependency health: External services, databases, caches

2. **Alerting Best Practices**:
   - Alert on symptoms, not causes
   - Reduce alert fatigue with proper thresholds
   - Implement escalation policies
   - Provide actionable information in alerts

3. **Observability Tools**:
   - Logging: ELK Stack, Graylog, Splunk
   - Metrics: Prometheus, Grafana, Datadog
   - Tracing: Jaeger, Zipkin, New Relic
   - APM: AppDynamics, Dynatrace

### **Disaster Recovery Planning**

1. **Backup Strategies**:
   - Full, incremental, and differential backups
   - Regular testing of restore procedures
   - Offsite storage and encryption

2. **Disaster Recovery Plans**:
   - Documented procedures for different failure scenarios
   - Regular drills and simulations
   - Clear roles and responsibilities

3. **DR Approaches**:
   - Pilot Light: Core systems running, others ready to scale up
   - Warm Standby: Scaled-down version of full environment
   - Hot Standby: Full duplicate environment ready to take over
   - Multi-Site Active/Active: Multiple active sites

### **Implementation Best Practices**

1. **Design for Failure**:
   - Assume components will fail
   - Test failure scenarios regularly (chaos engineering)
   - Document recovery procedures

2. **Automate Everything**:
   - Automated deployments and rollbacks
   - Automated scaling and failover
   - Automated testing and monitoring

3. **Implement Graceful Degradation**:
   - Identify critical vs. non-critical features
   - Design fallback mechanisms
   - Communicate status to users appropriately

4. **Regular Testing**:
   - Chaos engineering (e.g., Netflix Chaos Monkey)
   - Disaster recovery drills
   - Failover testing

5. **Documentation and Training**:
   - Clear runbooks for incident response
   - Cross-training team members
   - Post-incident reviews and continuous improvement

### **Real-World Examples**

1. **Netflix**:
   - Chaos Monkey deliberately terminates instances to test resilience
   - Multi-region deployment with active-active architecture
   - Circuit breakers to prevent cascading failures

2. **Amazon**:
   - Cell-based architecture isolates failures
   - Multiple availability zones per region
   - Extensive use of automated recovery

3. **Google**:
   - Global load balancing across data centers
   - Automated failover and recovery
   - Canary deployments to detect issues early

### **Conclusion**

Building highly available and resilient systems requires careful planning, appropriate architecture choices, redundancy at multiple levels, and continuous testing. By implementing the strategies outlined above, you can create systems that maintain operation even in the face of inevitable failures, providing a reliable experience for your users and protecting your business from costly downtime.
