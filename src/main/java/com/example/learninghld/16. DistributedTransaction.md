## **Distributed Transactions**

### **What is a Distributed Transaction?**

A distributed transaction is a database transaction that spans multiple databases or systems. It ensures that a set of operations across different services or databases either all succeed or all fail, maintaining data consistency in distributed systems.

### **Why Distributed Transactions are Important**

1. **Data Consistency**: Ensures that data remains consistent across multiple systems
2. **Business Integrity**: Maintains the integrity of business processes that span multiple services
3. **Fault Tolerance**: Provides mechanisms to handle failures in distributed environments
4. **System Integration**: Enables reliable integration between different systems and services

### **Challenges in Distributed Transactions**

1. **Network Reliability**: Networks can fail or experience latency
2. **Partial Failures**: Some participants may fail while others succeed
3. **Concurrency**: Multiple transactions may conflict with each other
4. **Heterogeneity**: Different systems may use different technologies and protocols
5. **Performance Impact**: Coordination overhead can significantly impact performance
6. **Scalability Limitations**: Many distributed transaction protocols don't scale well

### **ACID Properties in Distributed Context**

- **Atomicity**: All operations in the transaction complete successfully, or none do
- **Consistency**: The transaction brings the system from one valid state to another
- **Isolation**: Concurrent transactions don't interfere with each other
- **Durability**: Once committed, changes persist even in case of system failures

### **CAP Theorem Implications**

- Distributed transactions often sacrifice availability for consistency
- In partition scenarios, systems must choose between consistency and availability
- Different transaction protocols make different trade-offs within the CAP spectrum

### **2 Phase Commit (2PC)**

![img.png](../../../../resources/img_20.png)

- Each, coordinator and participants maintain log file for every step executed
- These things are used to resolve any failure at any stage
- In prepare phase, participants can use timed waiting and abort transaction if messages are lost
- In commit phase, its totally dependent on coordinator and hence participants are in blocked state. Here timed waiting is risky, so comes 3PC
- Everything happens in synchronous manner

**Detailed Explanation**:

The Two-Phase Commit protocol divides the transaction commit process into two phases:

1. **Phase 1: Prepare Phase**
   - Coordinator sends a prepare message to all participants
   - Each participant executes the transaction up to the point of commit
   - Participants vote YES (ready to commit) or NO (abort)
   - Participants write their decision to a durable log
   - If any participant votes NO, the entire transaction is aborted

2. **Phase 2: Commit/Abort Phase**
   - If all participants voted YES, coordinator sends commit message
   - If any participant voted NO, coordinator sends abort message
   - Participants complete the transaction according to the coordinator's decision
   - Participants acknowledge the completion
   - Coordinator records the final outcome

**Advantages**:
- Ensures atomicity across distributed systems
- Relatively simple to understand and implement
- Provides strong consistency guarantees
- Well-established protocol with wide support

**Disadvantages**:
- Blocking protocol: participants may block waiting for coordinator
- Single point of failure: if coordinator fails, participants may remain blocked
- Performance impact: requires multiple network round-trips
- Doesn't handle network partitions well
- Scales poorly with increasing number of participants

**Use Cases**:
- Traditional distributed database systems
- Enterprise application integration
- Financial transactions requiring strong consistency
- Resource management across multiple systems

### **3 Phase Commit (3PC)**

- Also, each participant can talk to another, to know their status
- These things are used to resolve any failure at any stage

![img_2.png](../../../../resources/img_22.png)

**Detailed Explanation**:

The Three-Phase Commit protocol adds an extra phase to address some limitations of 2PC:

1. **Phase 1: CanCommit Phase**
   - Coordinator sends canCommit message to all participants
   - Participants check if they can commit the transaction
   - Participants respond YES or NO without making any changes
   - This phase is a lightweight check before resources are locked

2. **Phase 2: PreCommit Phase**
   - If all participants voted YES in Phase 1, coordinator sends preCommit
   - Participants prepare the transaction and lock necessary resources
   - Participants write their decision to a durable log
   - Participants respond with ACK
   - If any participant voted NO in Phase 1, coordinator sends abort

3. **Phase 3: DoCommit Phase**
   - Coordinator sends doCommit message to all participants
   - Participants commit the transaction and release resources
   - Participants acknowledge completion
   - Coordinator records the final outcome

**Key Improvements Over 2PC**:
- Non-blocking in certain failure scenarios
- Participants can timeout and resolve transaction state by communicating with each other
- Better handling of coordinator failures
- Reduced vulnerability to network partitions

**Advantages**:
- More resilient to failures than 2PC
- Allows for timeout-based resolution
- Reduces blocking scenarios
- Participants can make progress even if coordinator fails

**Disadvantages**:
- More complex to implement than 2PC
- Additional network round-trip increases latency
- Still vulnerable to certain network partition scenarios
- Higher message overhead
- Not widely implemented in commercial systems

**Use Cases**:
- High-availability distributed systems
- Systems where coordinator failures are common
- Applications requiring stronger fault tolerance than 2PC
- Critical systems where blocking must be minimized

### **SAGA Pattern**

- Everything happens in async manner. Used when long running process

**Detailed Explanation**:

The Saga pattern is a sequence of local transactions where each transaction updates data within a single service. The completion of each local transaction triggers the next transaction in the saga. If a transaction fails, compensating transactions are executed to undo the changes made by the preceding transactions.

1. **Types of Saga Coordination**:
   - **Choreography**: Each service produces and listens to events, and decides when and how to execute local transactions
   - **Orchestration**: A central coordinator (orchestrator) directs the participants and manages the saga's execution

2. **Choreography-based Saga Flow**:
   - Service A completes transaction and publishes an event
   - Service B listens for the event and executes its transaction
   - Service B publishes its own event
   - Process continues through all required services
   - If any service fails, compensating events are published

3. **Orchestration-based Saga Flow**:
   - Orchestrator directs Service A to execute transaction
   - Service A reports completion to orchestrator
   - Orchestrator directs Service B to execute transaction
   - Process continues through all required services
   - If any service fails, orchestrator directs compensating transactions

**Advantages**:
- No distributed locking or two-phase commit required
- Highly scalable and suitable for microservices
- Supports long-running transactions
- Works well with eventual consistency models
- Resilient to partial failures
- Non-blocking and asynchronous

**Disadvantages**:
- Complex compensation logic required
- No isolation between transactions (dirty reads possible)
- Difficult to debug and track
- Eventual consistency may not be suitable for all use cases
- Requires careful design of compensating transactions

**Use Cases**:
- Microservices architectures
- Long-running business processes
- E-commerce order processing
- Travel booking systems
- Payment processing workflows
- Any process that spans multiple services and can tolerate eventual consistency

### **Comparison of Transaction Protocols**

| Feature | 2PC | 3PC | Saga |
|---------|-----|-----|------|
| Consistency | Strong | Strong | Eventual |
| Availability | Lower | Medium | Higher |
| Performance | Slower | Slower | Faster |
| Complexity | Medium | High | High |
| Blocking | Yes | Reduced | No |
| Scalability | Limited | Limited | High |
| Failure Recovery | Complex | Better | Built-in |
| Transaction Length | Short | Short | Can be long-running |

### **Other Distributed Transaction Approaches**

1. **Distributed Transaction Managers**:
   - **XA Standard**: Industry standard for distributed transaction processing
   - **JTA (Java Transaction API)**: Java-specific implementation of XA
   - **Atomikos**: Commercial transaction manager for Java applications
   - **Narayana**: Open-source transaction manager

2. **Try-Confirm-Cancel (TCC)**:
   - Business-oriented compensating transaction pattern
   - Three phases: Try (reserve resources), Confirm (complete operation), Cancel (compensate)
   - More application-specific than technical protocols
   - Requires explicit implementation of compensation logic

3. **Eventual Consistency with Reconciliation**:
   - Accept inconsistencies temporarily
   - Use background processes to detect and resolve inconsistencies
   - Often combined with event sourcing for auditability
   - Examples: bank statement reconciliation, inventory adjustments

### **Implementation Considerations**

1. **Transaction Boundaries**:
   - Keep transactions as small as possible
   - Identify clear boundaries between services
   - Consider business requirements for consistency

2. **Idempotency**:
   - Ensure operations can be safely retried
   - Use idempotency keys or tokens
   - Design compensating actions to be idempotent

3. **Monitoring and Observability**:
   - Track transaction states across services
   - Implement comprehensive logging
   - Set up alerts for stuck or failed transactions
   - Use distributed tracing to follow transaction flow

4. **Error Handling**:
   - Design clear failure modes
   - Implement retry mechanisms with backoff
   - Consider circuit breakers for failing services
   - Plan for partial failures and recovery

5. **Testing**:
   - Test failure scenarios thoroughly
   - Simulate network partitions and service failures
   - Verify compensating transactions work correctly
   - Use chaos engineering principles

### **Real-World Examples**

1. **Banking Systems**:
   - Fund transfers between accounts
   - Often use 2PC or XA transactions
   - Require strong consistency guarantees
   - May use reconciliation for cross-bank transfers

2. **E-commerce Platforms**:
   - Order processing across inventory, payment, shipping
   - Often use Saga pattern
   - Balance consistency with availability
   - Implement compensating actions for failures

3. **Travel Booking Systems**:
   - Coordinating flights, hotels, car rentals
   - May use a combination of approaches
   - Often implement reservation/confirmation pattern
   - Handle compensation for partial bookings

4. **Payment Processing**:
   - Credit card authorization and capture
   - Often use 2PC for internal systems
   - May use Saga for integration with external systems
   - Require careful handling of partial failures

### **Best Practices**

1. **Avoid Distributed Transactions When Possible**:
   - Redesign to keep related data together
   - Consider eventual consistency where appropriate
   - Use domain-driven design to identify boundaries

2. **Design for Failure**:
   - Assume any part of the system can fail
   - Plan recovery mechanisms for each failure mode
   - Implement comprehensive monitoring

3. **Balance Consistency Requirements**:
   - Not all operations need strong consistency
   - Identify which operations can use eventual consistency
   - Consider business impact of temporary inconsistencies

4. **Use Timeouts Wisely**:
   - Set appropriate timeouts for each phase
   - Implement escalation procedures for timeouts
   - Consider the impact of slow networks

5. **Document Transaction Flows**:
   - Create clear diagrams of normal and failure paths
   - Document compensation strategies
   - Ensure operational teams understand recovery procedures
