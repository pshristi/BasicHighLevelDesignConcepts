## **Designing an Idempotency Handler**

### **What is Idempotency?**

**Idempotency** refers to the property where multiple identical requests have the same effect as a single request.

Multiple retry should not cause a side-effect

In other words, if you perform the same operation multiple times, the result should be the same as if you had performed it just once.

### **Why is Idempotency Important?**

1. **Network Reliability**: Networks are inherently unreliable. Requests can fail, timeout, or responses can be lost.
2. **Client Retries**: Clients often implement retry mechanisms to handle transient failures.
3. **Preventing Duplicate Processing**: Without idempotency, retries can lead to duplicate operations (e.g., double charges, duplicate orders).
4. **User Experience**: Users may accidentally submit forms multiple times (double-clicking).
5. **Distributed Systems**: In distributed systems, failures are common and retries are necessary for resilience.

### **Common Scenarios Requiring Idempotency**

1. **Payment Processing**: Ensuring a customer is charged exactly once.
2. **Order Submission**: Preventing duplicate orders when a customer retries submission.
3. **Resource Creation**: Ensuring a resource is created only once despite multiple creation requests.
4. **Data Updates**: Making sure updates are applied correctly even if the same update is sent multiple times.
5. **Message Processing**: Processing each message exactly once in messaging systems.

### **Implementation Approaches**

- Will be done by attaching Idempotency key in headers of the POST request by client. Duplicate request will have same key.
- On backend, we will be storing key and its status (created/consumed) to see if request id processed with a key or not
- In case of concurrent request we must use lock. In distributed system, we can maintain locks by syncing caches

#### **1. Idempotency Key Generation**

**Client-Side Generation**:
- UUID/GUID: Universally unique identifiers
- Request hash: Hash of request payload
- Timestamp + client ID: Combination of timestamp and client identifier
- Transaction ID: Business-specific identifier

**Server-Side Generation**:
- Server can generate and return an idempotency key for subsequent retries
- Useful for multi-step operations

#### **2. Key Storage and Management**

**Storage Options**:
- In-memory cache (Redis, Memcached)
- Database table dedicated to idempotency keys
- Distributed cache for scalable systems

**Key Structure**:
```
{
  "idempotency_key": "uuid-or-hash",
  "status": "processing|completed|failed",
  "response": "cached_response_data",
  "created_at": "timestamp",
  "expires_at": "timestamp"
}
```

#### **3. Request Processing Flow**

1. **Receive Request**: Extract idempotency key from headers
2. **Check Key Status**:
   - If key doesn't exist: Process normally
   - If key exists with "processing" status: Wait or return 409 Conflict
   - If key exists with "completed" status: Return cached response
   - If key exists with "failed" status: Process or return error based on policy
3. **Set Key Status**: Mark as "processing"
4. **Process Request**: Execute the business logic
5. **Update Key Status**: Mark as "completed" or "failed"
6. **Store Response**: Cache the response for future duplicate requests
7. **Return Response**: Send response to client

#### **4. Handling Concurrent Requests**

- In case of concurrent request we must use lock. In distributed system, we can maintain locks by syncing caches
- **Distributed Locking**: Using Redis, ZooKeeper, or other distributed lock managers
- **Database Locks**: Using row-level locks or SELECT FOR UPDATE
- **Optimistic Concurrency Control**: Using version numbers or timestamps
- **Conflict Resolution**: Defining policies for handling concurrent identical requests

### **Implementation Challenges**

#### **1. Key Expiration**

- Keys should not be stored forever
- Appropriate TTL (Time-To-Live) depends on:
  - Business requirements
  - Client retry policies
  - Storage capacity

#### **2. Storage Scalability**

- High-volume systems generate many keys
- Partitioning/sharding strategies for key storage
- Cleanup processes for expired keys

#### **3. Exactly-Once Semantics**

- Ensuring operations are executed exactly once is challenging
- Need to handle partial failures and system crashes
- Transaction boundaries and atomicity

#### **4. Idempotency vs. Consistency**

- Balancing immediate consistency with performance
- CAP theorem considerations in distributed systems

### **Best Practices**

1. **Make Idempotency Keys Mandatory** for non-idempotent operations (POST, PATCH)
2. **Use Appropriate Key TTL** based on your retry policies
3. **Include Response Caching** to avoid reprocessing
4. **Document Idempotency Behavior** in API documentation
5. **Implement Monitoring** for duplicate requests and key usage
6. **Design for Failure** - handle partial failures gracefully
7. **Consider Business Context** when designing idempotency mechanisms

### **Real-World Examples**

1. **Stripe API**:
   - Uses `Idempotency-Key` header
   - Returns the same response for duplicate requests
   - Keys are valid for 24 hours

2. **AWS API**:
   - Uses `ClientRequestToken` parameter
   - Ensures idempotency for operations like EC2 instance creation

3. **Payment Gateways**:
   - Use transaction IDs to prevent double charges
   - Often have built-in idempotency mechanisms

### **Implementation Example (Pseudocode)**

```python
def process_request(request):
    idempotency_key = request.headers.get('Idempotency-Key')

    if not idempotency_key:
        return error_response("Idempotency-Key header is required")

    # Try to acquire lock for this key
    lock = distributed_lock_manager.acquire_lock(idempotency_key)

    if not lock:
        return error_response("Concurrent operation in progress", status=409)

    try:
        # Check if we've seen this key before
        stored_record = idempotency_store.get(idempotency_key)

        if stored_record:
            if stored_record.status == "completed":
                # Return cached response for completed requests
                return stored_record.response
            elif stored_record.status == "processing":
                # Another process is handling this request
                return error_response("Request is being processed", status=409)
            elif stored_record.status == "failed":
                # Previous attempt failed, we'll retry
                pass

        # Create or update record to indicate processing
        idempotency_store.set(
            idempotency_key,
            {
                "status": "processing",
                "created_at": current_timestamp(),
                "expires_at": current_timestamp() + TTL
            }
        )

        # Process the actual request
        try:
            result = business_logic.process(request.payload)

            # Update record with success and cache response
            idempotency_store.update(
                idempotency_key,
                {
                    "status": "completed",
                    "response": result,
                    "completed_at": current_timestamp()
                }
            )

            return result
        except Exception as e:
            # Update record with failure
            idempotency_store.update(
                idempotency_key,
                {
                    "status": "failed",
                    "error": str(e),
                    "failed_at": current_timestamp()
                }
            )
            raise
    finally:
        # Always release the lock
        distributed_lock_manager.release_lock(lock)
```

### **Conclusion**

Implementing proper idempotency handling is crucial for building reliable distributed systems. By using idempotency keys and appropriate storage mechanisms, you can ensure that operations are executed exactly once, even in the face of network failures and retries.
