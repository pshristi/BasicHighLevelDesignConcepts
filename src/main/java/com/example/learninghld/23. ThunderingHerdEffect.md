## **The Thundering Herd Effect**

### **What is the Thundering Herd Effect?**

The Thundering Herd Effect is a phenomenon that occurs when a large number of processes or clients simultaneously attempt to access a shared resource, causing system overload and degraded performance. This typically happens after the resource becomes available following a period of unavailability or when a cached item expires and needs to be regenerated.

### **Common Scenarios Where It Occurs**

1. **Cache Stampede**: When a popular cached item expires and multiple clients try to regenerate it simultaneously
2. **Database Overload**: When connection pools are exhausted and multiple clients wait for connections to become available
3. **API Rate Limiting**: When clients hit rate limits and implement synchronized retry mechanisms
4. **Service Recovery**: When a service comes back online after downtime and receives a flood of accumulated requests
5. **Scheduled Tasks**: When many tasks are scheduled to run at the same time (e.g., midnight jobs)
6. **DNS Failover**: When DNS changes propagate and redirect traffic to backup systems

### **Impact on Systems**

- **Resource Exhaustion**: CPU, memory, connection pools, and thread pools can be quickly depleted
- **Cascading Failures**: Overload of one component can trigger failures in dependent systems
- **Increased Latency**: Response times increase dramatically during these events
- **Service Unavailability**: In worst cases, services become completely unresponsive
- **Wasted Resources**: Many redundant operations may be performed (e.g., multiple identical database queries)

### **Mitigation Strategies**

When a sudden spike in traffic comes, we should handle it in below ways

- Proper retry
  - Use exponential backoff in retry (Base * 2^n)
  - Use Jitter in exponential backoff to bring randomness (Min(Max wait time, rand(0, base*2^n)))
- Use rate limiter at api gateway itself, before reaching traffic at LB
  - Can use token bucket to smoothen the sudden spike
- Auto scale the system

#### **Detailed Retry Strategies**

1. **Exponential Backoff**:
   - Start with a base delay (e.g., 100ms)
   - For each retry, multiply the delay by a factor (typically 2)
   - Example: 100ms → 200ms → 400ms → 800ms → etc.
   - Prevents immediate retry storms while giving the system time to recover
   - Implementation example:
     ```
     baseDelay = 100ms
     maxDelay = 10s
     for retry = 1 to maxRetries:
         delay = min(maxDelay, baseDelay * 2^(retry-1))
         wait(delay)
         attempt request
     ```

2. **Jitter (Randomized Backoff)**:
   - Add randomness to the delay calculation
   - Prevents synchronized retries from multiple clients
   - Spreads the load more evenly over time
   - Implementation example:
     ```
     baseDelay = 100ms
     maxDelay = 10s
     for retry = 1 to maxRetries:
         exponentialDelay = min(maxDelay, baseDelay * 2^(retry-1))
         jitteredDelay = exponentialDelay * (0.5 + random(0, 0.5))
         wait(jitteredDelay)
         attempt request
     ```

#### **Advanced Rate Limiting Techniques**

1. **Token Bucket Algorithm**:
   - Tokens are added to a bucket at a constant rate
   - Each request consumes a token
   - When the bucket is empty, requests are either queued or rejected
   - Allows for bursts of traffic while maintaining a long-term rate limit

2. **Leaky Bucket Algorithm**:
   - Requests enter a queue (the bucket)
   - Requests are processed at a constant rate
   - When the queue is full, new requests are rejected
   - Provides a consistent outflow rate, smoothing out bursts

3. **Adaptive Rate Limiting**:
   - Dynamically adjust rate limits based on system load
   - Tighten limits when resources are constrained
   - Relax limits when resources are abundant
   - Requires monitoring of system health metrics

#### **Cache Optimization Strategies**

1. **Cache Warming**:
   - Proactively refresh cache items before they expire
   - Use background processes to update cache entries
   - Prevents cache misses during high-traffic periods

2. **Cache Stampede Prevention**:
   - **Probabilistic Early Expiration**: Randomly refresh before expiration
   - **Semaphore Locks**: Only allow one process to regenerate a cached item
   - **Work Coalescing**: Multiple requests for the same uncached data are collapsed into one backend request
   - **Stale-While-Revalidate**: Serve stale content while asynchronously refreshing

3. **Cache Hierarchies**:
   - Implement multiple layers of caching (browser, CDN, application, database)
   - Each layer reduces load on subsequent layers
   - Distribute cache invalidation to avoid simultaneous expiration

#### **Load Balancing and Queueing**

1. **Intelligent Load Balancing**:
   - Use algorithms that consider server load, not just round-robin
   - Implement health checks to avoid routing to overloaded servers
   - Consider geographic distribution to spread load across regions

2. **Request Queuing**:
   - Queue requests when backend services are overloaded
   - Process queued requests at a sustainable rate
   - Implement priority queues for critical operations

3. **Circuit Breakers**:
   - Detect when a service is struggling and stop sending requests
   - Prevent cascading failures by failing fast
   - Gradually test recovery with a limited number of requests

#### **Auto-Scaling Best Practices**

1. **Predictive Scaling**:
   - Scale resources based on historical patterns before traffic arrives
   - Use machine learning to predict traffic patterns
   - Pre-warm systems for known traffic events (sales, product launches)

2. **Gradual Scaling**:
   - Avoid scaling too quickly, which can cause its own instability
   - Implement step scaling policies with cooldown periods
   - Monitor the effect of scaling actions before taking additional steps

3. **Resource Buffering**:
   - Maintain a buffer of spare capacity at all times
   - Accept higher costs for improved reliability
   - Particularly important for stateful services that take time to initialize

### **Real-World Examples**

1. **Netflix Chaos Engineering**:
   - Proactively tests systems against traffic spikes and failures
   - Implements client-side load balancing with intelligent retry mechanisms
   - Uses adaptive concurrency limits to prevent overload

2. **Amazon Prime Day Preparation**:
   - Gradually ramps up capacity ahead of known traffic events
   - Implements service quotas and prioritization
   - Uses extensive monitoring to detect and respond to bottlenecks

3. **Google's Global Load Balancing**:
   - Distributes traffic across multiple regions
   - Implements request coalescing for popular resources
   - Uses advanced caching strategies to minimize backend load

### **Monitoring and Detection**

1. **Key Metrics to Watch**:
   - Request rate and error rate
   - Response time percentiles (p50, p95, p99)
   - Queue depths and processing rates
   - Resource utilization (CPU, memory, connections)

2. **Early Warning Systems**:
   - Set alerts for sudden changes in traffic patterns
   - Monitor for increased retry rates
   - Track cache hit ratios and database load

3. **Post-Incident Analysis**:
   - Conduct thorough reviews after thundering herd incidents
   - Identify bottlenecks and failure points
   - Implement improvements to prevent recurrence
