# Elasticsearch

## What Is Elasticsearch?
- Elasticsearch is a NoSQL database.
- ElasticSearch is an open source Search Engine based on Apache Lucene as inverted Text Data structure and it is built with RESTful APIS.
    - Written in Java. Act as a high-level orchestration framework over Lucene
    - inverted Text Data structure : helps in full text search
- We use it for Storing, searching and Managing
    - Logs
    - Search Backend with terrific speed and flexibility.

### Why ES? Most Common Usage of ElasticSearch
- In Autocomplete in search Box FrontEnd.
- If you hit Normal DB then Client will wait for a lot of time till it fetch the data and if it change again in worst case the time doubles again
- Such a poor User Experience is not acceptable in User friendly apps.
- Hence ElasticSearch came in for the Rescue.
- Elasticsearch is a fast, distributed , reliable search engine:

## Core Data Model
- It mainly consist of
    - Indexes - similar to Database in relational Terms
    - Documents - Rows - JSON objects
    - Fields - Columns
    - Mapping - used to define field data types. Its good to define mapping while creating a index to avoid elastic search doing random guess on datatype and their intended use-case

### What Is a Document in ElasticSearch?
- The document is very similar to a row in relational databases. Every document in the index possess different structure but has the same data type for respective fields.
- MySQL = Databases = Tables = Columns/Rows
- ElasticSearch = Indices = Types = Documents with Properties
- Type : A **type** was an old Elasticsearch feature used to logically group different kinds of documents inside the same index, similar to tables in a database, but it has been removed in modern Elasticsearch versions.
- An Elasticsearch cluster can contain multiple Indices (databases), which in turn contain multiple Types (tables). These types hold multiple Documents (rows), and each document has Properties (columns). EG = University - (students, teachers, subjects) - all internal details of that type

### Read and Write Operations
- It mainly has Read and write operation. you need to update this as soon as you update the main Database and Read it when needs Autocomplete feature.
    - When we index a doc, es returns id with version which can be used to handle collision while update operation
    - Put request for an existing doc id, updated whole doc. For particular field update we can use post docId with details of that particular field for field by field update

## Cluster Architecture

### What Is a Cluster in Elasticsearch? Explain Node?
- Cluster is a collection of single or multiple nodes that holds your entire data and offers centralized indexing and search abilities across all nodes.
- A node is an elastic search Instance. It is created when an elasticsearch instance begins.
    - Master Node
    - Coordinating Node : Responsible for search query planning
    - Data Node
    - Ingest Node : Responsible for inserting data
    - ML Node

## Shards and Replicas
- Shard: The data stored in an index can be divided into multiple partitions. Each of these partitions is called Shard, which is managed and controlled by a separate node. An Elasticsearch index has 5 shards by default. For an index, you can easily specify how many shards you want. As a result, every shard is its own, fully functional, and independent "index", which can run on any node in a cluster.
    - A **shard** is a physical piece of an Elasticsearch index. Elasticsearch automatically breaks an index into shards so data can be stored across multiple servers.
    - When a document is indexed, Elasticsearch computes: `hash(document_id) % number_of_shards` to decide which shard gets the document.
    - A database partition key and Elasticsearch routing key serve similar purposes: they control where data is stored and allow queries to target a subset of storage units. By default, Elasticsearch distributes documents using the document ID hash and searches all shards, but custom routing can be used to co-locate related documents on the same shard and query only that shard, reducing search fan-out and improving performance.
    - Inside each shard there are multiple immutable segments containing documents
- Replica: As the name implies, replicas are Elasticsearch fail-safe mechanisms, and are essentially copies of an index's shards. As a backup, this could come in handy when a node crashes. Furthermore, replicas can serve read requests, which is useful for increasing search performance. To ensure high availability, replicas must not be placed on the same node as the original shard (called the "primary shared") from which they were replicated

## Querying and Indexing Internals

### Query Language
- Apache Lucene query language, which is also known as Query DSL (Domain Specific Language), is used by Elasticsearch.
- ES also support `_scripts` called painless for computation.

### Inverted Index
- Map of tokens (keywords) to address of docIds containing them
- Doc Values : The doc values structure does just this with a columnar, contiguous representation of a single field for all documents across the segment.

### Text vs. Keyword Fields
- Any text field can be stored as text as well as keyword. Text field is stored as token and can be used for fulltext search while keyword supports exact match
    - Nested fields can be created for each document when either text plus keyword needs to be stored or when we need quick filtering based on parent document data.
    - Text fields are analyzed at indexing and can be searched using match queries
    - Keyword fields are not analysed and supports term query
    - A common mapping: text + keyword Example

```
{
  "title": {
    "type": "text",
    "fields": {
      "keyword": {
        "type": "keyword"
      }
    }
  }
}
```

## Pagination: Scroll vs. Search-After

### Scroll
- Scroll : A scrollId is a cursor-like token returned by Elasticsearch that lets you fetch large search results in batches while maintaining a consistent snapshot of the data.

> Start scroll -> Freeze view of index -> Read through that frozen view

### Search-After
- Search-after is better alternative as it is stateless. Elasticsearch uses the point in time (PIT) API in conjunction with search_after for cursor-based pagination.

## Scripting (Painless) and Computed Fields

### Script Fields
- ES also supports custom computation and aggregation
    - Normally calculated during search but can be stored at index time. This can be done:
        - In your application before indexing
        - Using an ingest pipeline with a script processor
    - Script contains Painless query : Painless is Elasticsearch's scripting language.
    - Example custom computed field

```
{
  "script_fields": {
    "new_field": {
      "script": {
        "source": "calculation"
      }
    }
  }
}
```

- Example aggregation

```
{
  "aggs": {
    "name": {
      "aggregation_type": {
        "field": "field_name"
      }
    }
  }
}
```

### Common Real-World Examples

**Script field**
```
{
  "script_fields": {
    "full_name": {
      "script": {
        "source": "doc['first_name.keyword'].value + ' ' + doc['last_name.keyword'].value"
      }
    }
  }
}
```

**Script query**
```
{
  "query": {
    "script": {
      "script": {
        "source": "doc['salary'].value > 100000"
      }
    }
  }
}
```

**Script aggregation**
```
{
  "aggs": {
    "total_revenue": {
      "sum": {
        "script": {
          "source": "doc['price'].value * doc['quantity'].value"
        }
      }
    }
  }
}
```

**Ingest pipeline script**
```
{
  "script": {
    "source": "ctx.total = ctx.price * ctx.quantity"
  }
}
```

### A Useful Rule
- If the value is used rarely, calculate it with a script during search.
- If the value is used often (sorting, filtering, aggregations on every request), calculate it once during indexing and store it as a normal field. This is usually much faster and more scalable.

## The ELK Stack

### What Is the ELK Stack?
- The ELK Stack is a collection of three open-source products - Elasticsearch, Logstash, and Kibana. They are all developed, managed, and maintained by the company Elastic.
- E stands for ElasticSearch: is a NoSQL database tool, which is used to store the unstructured data. It is used for storing logs.
- L stands for LogStash: It is used for both shipping as well as the processing and storing logs. It is a log pipeline tool to perform transformation on data. It takes input from different sources and performs various transformations on it. At last, it exports the data into various targets.
- K stands for Kibana: is a data visualization tool, which provides an interactive UI (User Interface) to the users for data visualization.

### ELK Stack Architecture
- ELK Stack is designed to allow users to talk to data from any source, in any format, and to search, analyze, and visualize that data in real-time.
- Logs: Server logs that need to be analyzed are identified
- Logstash: Collect logs and events data. It even parses and transforms data.
- ElasticSearch: The transformed data from Logstash is Store, Search, and indexed.
- Kibana: Kibana uses Elasticsearch DB to Explore, Visualize, and Share
- ELK can be used for APM (Application performance management)
