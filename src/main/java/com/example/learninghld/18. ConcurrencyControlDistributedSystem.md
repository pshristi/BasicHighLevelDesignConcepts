## **Concurrency Control in Distributed Systems**

Synchronised (critical section) will not work in Distributed system scenario, where comes use of Distributed concurrency control

### **Understanding Transactions**

- What is the usage of Transaction?
  - Transaction helps to achieve INTEGRITY. Means it help us to avoid INCONSISTENCY in our database.
  - **Definition**: A transaction is a sequence of operations performed as a single logical unit of work
  - **ACID Properties**:
    - **Atomicity**: All operations complete successfully or none do
    - **Consistency**: Database remains in a consistent state before and after transaction
    - **Isolation**: Concurrent transactions don't interfere with each other
    - **Durability**: Once committed, changes persist even in case of system failures
  - **Importance in Distributed Systems**:
    - Maintains data integrity across multiple nodes
    - Coordinates operations spanning multiple services
    - Handles partial failures gracefully
    - Provides consistency guarantees in distributed environments

### **Database Locking Mechanisms**

- What is DB Locking?
  - DB Locking, help us to make sure that no other transaction update the locked rows.
  - Shared locks are also known as read locks 
    ![img.png](../../../../resources/img_27.png)
  - **Types of Locks**:
    - **Shared (S) Locks**: Allow multiple transactions to read data simultaneously
    - **Exclusive (X) Locks**: Prevent other transactions from reading or writing data
    - **Intent Locks**: Indicate intention to acquire locks at a finer granularity
    - **Update Locks**: Initially allow reads but can be promoted to exclusive locks
  - **Lock Granularity**:
    - **Row-Level Locks**: Lock individual rows (fine-grained, higher concurrency)
    - **Page-Level Locks**: Lock database pages containing multiple rows
    - **Table-Level Locks**: Lock entire tables (coarse-grained, lower concurrency)
    - **Database-Level Locks**: Lock entire database (very restrictive)
  - **Lock Duration**:
    - **Short-Term Locks**: Released immediately after operation
    - **Long-Term Locks**: Held until transaction completes

### **Transaction Isolation Problems**

- Dirty Read:
  - If Transaction A is reading the data which is writing by Transaction B and not yet even committed. If Transaction B does the rollback, then whatever data read by Transaction A is know dirty read.
  ![img_2.png](../../../../resources/img_29.png)
  - **Impact**: Can lead to decisions based on data that never actually existed
  - **Example**: Reading a bank account balance after a deposit but before commit, then the deposit is rolled back
  - **Prevention**: Use higher isolation levels (Read Committed or above)

- Non-Repeatable Read :
  - If suppose Transaction A, reads the same row several times and there is a chance that it reads different value.
  ![img_3.png](../../../../resources/img_30.png)
  - **Impact**: Can lead to inconsistent processing within a single transaction
  - **Example**: Reading a product price twice during order processing, but price changes between reads
  - **Prevention**: Use Repeatable Read isolation level or higher

- Phantom Read : 
  - If suppose Transaction A, executes same query several times and there is a chance that the rows returned are different.
  ![img_4.png](../../../../resources/img_31.png)
  - **Impact**: Can lead to incorrect aggregations or processing of collections
  - **Example**: Counting available seats on a flight, then processing based on that count, but new seats were added
  - **Prevention**: Use Serializable isolation level

### **Transaction Isolation Levels**

- What are the Isolation Level present?
    ![img_5.png](../../../../resources/img_32.png)
- Read uncommited to be used only for read heavy
  ![img_1.png](../../../../resources/img_28.png)

- **Read Uncommitted**:
  - Lowest isolation level
  - Allows dirty reads, non-repeatable reads, and phantom reads
  - Provides maximum concurrency but minimum consistency
  - Use cases: Report generation where approximate values are acceptable

- **Read Committed**:
  - Prevents dirty reads
  - Still allows non-repeatable reads and phantom reads
  - Each query sees only committed data
  - Default isolation level in many databases (PostgreSQL, Oracle)
  - Use cases: General-purpose OLTP applications

- **Repeatable Read**:
  - Prevents dirty reads and non-repeatable reads
  - Still allows phantom reads
  - Ensures same rows return same values throughout transaction
  - Default isolation level in MySQL/InnoDB
  - Use cases: Financial calculations requiring consistent views

- **Serializable**:
  - Highest isolation level
  - Prevents all concurrency phenomena
  - Transactions execute as if they were serialized one after another
  - Lowest concurrency but highest consistency
  - Use cases: Financial transactions, critical data operations

### **Concurrency Control Approaches**

- Optimistic concurrency control
  - Version column is used to acheive this
  - Isolation Level used Below REPEATABLE READ (read commited)
  - Much Higher Concurrency
  - No chance of Deadlock
  - In case of conflict, overhead of transaction rollback and retry logic is there.
  ![img_6.png](../../../../resources/img_33.png)
  ![img_7.png](../../../../resources/img_34.png)
  - **How It Works**:
    - Assumes conflicts are rare
    - Transactions operate on local copies of data
    - Before commit, system checks if data has changed
    - If conflict detected, transaction aborts and retries
  - **Implementation Methods**:
    - Timestamp ordering
    - Multi-version concurrency control (MVCC)
    - Validation techniques
  - **Best For**:
    - Read-heavy workloads
    - Low-contention environments
    - Short transactions
    - Web applications with many users but few conflicts

- Pessimistic concurrency control
  - Isolation Level used REPEATABLE READ and SERIALIZABLE
  - Less Concurrency compared to Optimistic.
  - Deadlock is Possible, then transactions stuck in deadlock are forced to do rollback.
  - Putting a long lock, sometimes timeout issue comes and rollback need to be done.
  - **How It Works**:
    - Assumes conflicts are likely
    - Locks resources before accessing them
    - Holds locks until transaction completes
    - Other transactions wait for locks to be released
  - **Implementation Methods**:
    - Two-phase locking (2PL)
    - Strict two-phase locking
    - Deadlock detection and prevention
  - **Best For**:
    - Write-heavy workloads
    - High-contention environments
    - Critical data integrity requirements
    - Financial systems where conflicts must be prevented

### **Distributed Concurrency Control Challenges**

- **Network Latency**:
  - Lock acquisition and release takes longer
  - Increases transaction duration
  - Higher chance of conflicts
  - Solutions: Local caching, optimistic approaches

- **Partial Failures**:
  - Nodes holding locks may fail
  - Can lead to indefinite blocking
  - Solutions: Lock timeouts, heartbeats, recovery protocols

- **Clock Synchronization**:
  - Timestamp-based approaches require synchronized clocks
  - Clock drift can cause incorrect ordering
  - Solutions: Logical clocks, vector clocks, hybrid approaches

- **Scalability Limitations**:
  - Centralized lock managers become bottlenecks
  - Distributed lock management adds complexity
  - Solutions: Partitioning, local lock management, lock-free algorithms

### **Modern Distributed Concurrency Control Techniques**

- **Multi-Version Concurrency Control (MVCC)**:
  - Maintains multiple versions of data
  - Readers never block writers and vice versa
  - Each transaction sees a consistent snapshot
  - Used in PostgreSQL, Oracle, MySQL InnoDB

- **Timestamp Ordering**:
  - Assigns timestamps to transactions
  - Ensures transactions execute in timestamp order
  - Can be combined with MVCC for better performance
  - Variants: Basic TO, Multiversion TO, Optimistic TO

- **Distributed Two-Phase Locking**:
  - Extends 2PL to distributed environments
  - Coordinates lock acquisition across nodes
  - Often combined with two-phase commit for atomicity
  - Challenges: Deadlocks, performance overhead

- **Conflict-Free Replicated Data Types (CRDTs)**:
  - Special data structures that can be updated concurrently
  - Automatically resolve conflicts
  - No need for explicit locking
  - Used in eventually consistent systems

- **Consensus Algorithms**:
  - Paxos, Raft, ZAB (Zookeeper Atomic Broadcast)
  - Ensure agreement on transaction order
  - Provide strong consistency guarantees
  - Used in distributed coordination services

  - Distributed lock services (e.g., Zookeeper, etcd)

  - Serverless transaction coordination

- **Financial Systems**:
  - Hybrid approaches combining optimistic and pessimistic techniques
  - Custom isolation levels for specific requirements
  - Specialized conflict resolution strategies
