## SQL vs NoSQL
### Introduction

**SQL databases**
SQL (structured query language) databases are essentially relational databases, meaning that data is organized in terms of their relationships with other data.

**NoSQL databases**
NoSQL (not only SQL) databases, on the other hand, are non-relational. There are several types of NoSQL databases, such as column-oriented, graph-based, document-oriented, and key-value store databases

### Detailed Comparison

**SQL**

Structure
- Table, row, column
- Predetermined schema
- Relation b/w diff tables
- Fixed schema that must be defined before data is added
- Enforces data integrity through foreign keys, constraints
- Examples: MySQL, PostgreSQL, Oracle, SQL Server, SQLite

Nature
- Concentrated/centralized
- Typically runs on a single server (with replicas for redundancy)
- Strong consistency model
- Optimized for storage efficiency and data integrity

Scalability
- Vertical
- Scale by adding more CPU, RAM, or storage to existing server
- Limited by hardware capabilities of a single machine
- Can be challenging to scale beyond certain limits
- Read scalability through read replicas

Property
- ACID : Data Integrity/Consistency
  - **A**tomicity: Transactions are all-or-nothing
  - **C**onsistency: Data remains in a valid state
  - **I**solation: Transactions don't interfere with each other
  - **D**urability: Committed changes are permanent

Query Language
- Standardized SQL with powerful querying capabilities
- Supports complex joins, aggregations, and subqueries
- Declarative language (specify what, not how)

**NoSql**

Structure
- Unstructured data :
  - Key Value DB : Can search only on keys
    - Simple data structure storing values against keys
    - Extremely fast for simple operations
    - Examples: Redis, DynamoDB, Riak
  - Document DB : Can search on keys as well as values
    - Stores data in JSON-like documents
    - Schema flexibility allows for nested data
    - Examples: MongoDB, CouchDB, Firestore
  - Graph DB
    - Optimized for complex relationships between entities
    - Uses nodes, edges, and properties
    - Examples: Neo4j, Amazon Neptune, JanusGraph
  - Columnwise DB
    - Stores data in column families
    - Optimized for analytical queries and large datasets
    - Examples: Cassandra, HBase, Google Bigtable

Nature
- Distributed
- Designed to run across multiple servers/nodes
- Data is typically replicated across nodes
- Built for high availability and partition tolerance

Scalability
- Horizontal
- Scale by adding more servers to the cluster
- Can scale to massive datasets and high throughput
- Often designed with built-in sharding capabilities
- Linear performance scaling with additional nodes

Property
- BASE : Basically availability, Safe state, Eventual consistency
  - **B**asically **A**vailable: System guarantees availability
  - **S**oft state: State may change over time without input
  - **E**ventual consistency: System will become consistent over time

Query Language
- Varies by database type
- Often proprietary or database-specific
- May support SQL-like queries (e.g., MongoDB's query language)
- Some offer limited join capabilities

### SQL-Specific Constructs

Relational databases provide built-in schema objects that NoSQL databases generally don't offer, further reinforcing the structural rigor of SQL:

#### Views
A virtual table defined by a stored query — useful for simplifying repeated joins or restricting access to specific columns.

- Create:
  ```sql
  CREATE VIEW view_name AS
  SELECT column1, column2, ...
  FROM table_name
  WHERE condition;
  ```
- Create using multiple tables:
  ```sql
  CREATE VIEW view_name AS
  SELECT table_name1.Col1, table_name1.Col2, table_name2.Col1
  FROM table_name1, table_name2
  WHERE condition;
  ```
- Update (redefine):
  ```sql
  CREATE OR REPLACE VIEW view_name AS
  SELECT column1, column2, ...
  FROM table_name
  WHERE condition;
  ```
- Insert values into a view:
  ```sql
  INSERT INTO view_name (column1, column2, column3, ...)
  VALUES (value1, value2, value3, ...);
  ```
- Delete values from a view:
  ```sql
  DELETE FROM view_name
  WHERE condition;
  ```
- Drop:
  ```sql
  DROP VIEW view_name;
  ```

#### Indexes
Speed up `SELECT`/`WHERE` lookups at the cost of slower `INSERT`/`UPDATE` (the index itself needs updating). Can be single-level (primary, clustered, secondary) or multi-level (B-Tree, B+ Tree).

- Create:
  ```sql
  CREATE INDEX index_name
  ON table_name (column1, column2, ...);
  ```
- Rename:
  ```sql
  ALTER INDEX old_index_name RENAME TO new_index_name;
  ```
- Drop:
  ```sql
  DROP INDEX index_name;
  ```

#### Sequences
Auto-generate unique numeric values (e.g., for primary keys), independent of any specific table.

- Create:
  ```sql
  CREATE SEQUENCE sequence_name
  START WITH initial_value
  INCREMENT BY increment_value
  MINVALUE minimum_value
  MAXVALUE maximum_value
  CYCLE | NOCYCLE;
  ```
- Use in an insert:
  ```sql
  INSERT INTO table_name VALUES (sequence_name.nextval);
  ```

### When to Choose SQL

1. **Data has a clear, unchanging structure**
   - When your schema is well-defined and unlikely to change frequently
   - Example: Financial applications, ERP systems

2. **Complex queries and transactions are required**
   - When you need to perform complex joins across multiple tables
   - Example: Business intelligence applications, reporting systems

3. **ACID compliance is necessary**
   - When data integrity is critical and transactions must be reliable
   - Example: Banking systems, payment processing

4. **Relationships between data entities are complex**
   - When your data has many relationships that need to be enforced
   - Example: Social networks (though many now use a hybrid approach)

### When to Choose NoSQL

1. **Schema flexibility is needed**
   - When your data structure may evolve or is not fully defined
   - Example: Content management systems, product catalogs

2. **Massive scale is anticipated**
   - When you need to handle extremely large volumes of data or traffic
   - Example: IoT applications, log analytics

3. **High availability is critical**
   - When your system needs to remain available despite network partitions
   - Example: Global services that can't afford downtime

4. **Data is naturally document-oriented or graph-based**
   - When your data fits naturally into documents or graph structures
   - Example: User profiles (documents), recommendation engines (graphs)

### Real-world Examples

**SQL Use Cases**
- Traditional banking systems (MySQL, Oracle)
- Airline reservation systems (SQL Server)
- Enterprise resource planning (PostgreSQL)
- Traditional e-commerce platforms (MySQL)

**NoSQL Use Cases**
- Social media content (MongoDB for posts, Neo4j for connections)
- Real-time big data applications (Cassandra)
- Caching and session storage (Redis)
- Product catalogs with varying attributes (MongoDB)
- High-traffic web applications (DynamoDB)

### Hybrid Approaches

Many modern systems use both SQL and NoSQL databases:
- SQL for transactional data requiring ACID properties
- NoSQL for high-volume data, caching, or specialized data models
- Example: E-commerce platform using PostgreSQL for orders and payments, MongoDB for product catalog, and Redis for session management

### Selection Criteria

When choosing between SQL and NoSQL, consider:
1. **Data structure**: Is your data structured or unstructured?
2. **Scale requirements**: What volume of data and traffic do you anticipate?
3. **Consistency needs**: Is strong consistency required, or is eventual consistency acceptable?
4. **Development velocity**: How frequently will your schema change?
5. **Query patterns**: What types of queries will your application perform?
6. **Team expertise**: What databases is your team familiar with?
7. **Budget constraints**: What are the licensing and operational costs?
