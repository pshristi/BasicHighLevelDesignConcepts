# Core Concepts & Architecture

## What is Apache Pulsar?

Apache Pulsar is a distributed event streaming and messaging platform designed for high throughput, low latency, multi-tenancy and geo-replication. Unlike Kafka, Pulsar separates compute (Broker) from storage (BookKeeper), allowing independent scaling of both. It supports both queue and pub-sub messaging with built-in features like retries, dead-letter queues, schema management and geo-replication.

## High-Level Architecture

### Components

|---------------------------------------------|-----------------------------------------------------------------|
| Producer                                    | Publishes messages                                              |

| BookKeeper                                  | Stores messages persistently in replicated ledgers.             |

## Core Terminology

### Topic

A logical channel where producers publish messages.

### Partition

A topic can be divided into multiple partitions.

#### Why partitions?

- Higher throughput
- Horizontal scalability

#### Trade-off

- Ordering is guaranteed only within a partition, not across partitions.

### Message Key

- If a message key is present, Pulsar hashes the key so the same key consistently goes to the same partition.
- If no key is present, the producer's routing mode (such as round-robin) determines the partition.
- Each partition is then consumed independently, allowing higher throughput and parallelism.

### Cursor

A cursor tracks how far a subscription has consumed. Each subscription maintains its own cursor. That's why multiple subscriptions can consume the same topic independently.

## Queue vs Pub-Sub

- Queue : One message -> One consumer
- Pub-Sub : One message  -> Many independent subscriptions

## Persistent vs Non-Persistent Topics

### Persistent (Default)

- Stored in BookKeeper
- Can be replayed
- Survives broker restarts
- Used in production

### Non-Persistent

- Stored in broker memory
- Lower latency
- Data loss acceptable
- Rarely used in enterprise systems

## Producer Lifecycle

A Producer is responsible for publishing messages to a topic.
Once the Broker receives a message:
- It persists it to BookKeeper.
- Waits for required acknowledgements.
- Returns success to the producer.

### Producer Modes

#### Synchronous Send

- Blocks until ACK is received.
- Simpler.
- Higher latency.
- Use when Financial transactions or Critical workflows

#### Asynchronous Send

- Doesn't block the application thread.
- Better throughput.
- Preferred for high-volume event publishing.

## Consumer Lifecycle

Consumers subscribe to a topic and process messages. Unlike Kafka polling, Broker pushes messages and consumer receives and send ACK/NACk

### Message Acknowledgement

ACK

- Message processed successfully.
- Broker marks it as acknowledged.
- Consumer won't receive it again.

NACK 

- Temporary processing failure
- Downstream service unavailable
- Retry expected

### ACK Timeout

The broker waits for a configured duration. If no ACK arrives, the message is considered unprocessed and is delivered again. This behavior underpins Pulsar's default at-least-once delivery guarantee.
ACK do not deletes the message immediately. It advances the subscription cursor; retention policies determine storage.

## Delivery Guarantees

| Guarantee     | Meaning                                                 |
|---------------|---------------------------------------------------------|
| At-most-once  | May lose messages                                       |
| At-least-once | May deliver duplicates                                  |
| Exactly-once  | No duplicates (using transactions + application design) |

Default is At-Least-Once. If Pulsar retries messages, consumers should be idempotent.

## Subscription Types

### Exclusive
- Only one consumer is allowed.
- Advantages is Strong ordering, Simple
- Drawback is No horizontal scaling
- Use Cases : Scheduled jobs, Singleton processing

### Failover
- Only one consumer processes messages. If the active consumer fails, the standby automatically becomes active.
- Advantages is High availability, Ordering preserved
- Drawback is Limited parallelism

### Shared

- Messages are distributed across consumers. Each message is processed by exactly one consumer in the subscription.
- How does Pulsar ensure this? 
- Broker maintains: Connected consumers, In-flight messages, ACK status
- If a Consumer crashes, the broker redelivers the unacknowledged message to another consumer. This provides load balancing while ensuring no acknowledged message is processed twice by the same subscription.
- Advantages is Maximum throughput, Horizontal scaling
- Drawback is Ordering is not guaranteed.

### Key_Shared

- Instead of round-robin, messages are routed using the message key.
- Every message with the same key, always goes to the same consumer.
- What if the Consumer crashes? 
- Broker reassigns ownership of that key. Unacknowledged messages are delivered again. Ordering for that key continues, but duplicates remain possible. Therefore, Consumers must be idempotent.

## Ordering

- Ordering exists only within a partition.
- To preserve ordering for an entity, publish every event with the same message key.
- Pulsar doesn't guarantees global ordering.

## Idempotency

- Unique Event ID
- Database unique constraint
- UPSERT
- Processed-event table
- Business key deduplication

## Consumer Permits

Consumer says : I can currently process 500 messages. Broker will never send more than 500. As messages are processed, consumer automatically grants more permits.
Permits provide built-in backpressure.

## receiverQueueSize

- What it is? : Number of messages buffered inside the consumer client.
- It defines how many messages the client prefetches and buffers locally. A larger queue improves throughput by reducing network round trips but increases memory usage and the number of in-flight messages.
- Notice : Application isn't talking directly to Broker. It usually consumes from the local queue.
- Benefits : Higher throughput, Lower network latency
- Trade-off : Higher memory usage, Longer failover (more in-flight messages)

## receive() vs MessageListener

There are two distinct consumption models:

Synchronous (pull) model using receive()
- Your application explicitly calls consumer.receive().
- The calling thread blocks until a message is available (or until a timeout if you use receive(timeout)).
- No message listener or listener thread is involved.
- Good for: Custom retries, Batch processing, Complex workflows

Asynchronous (push) model using messageListener()
- You register a MessageListener.
- Broker creates and manages threads that invoke your listener whenever messages arrive.
- You should not call receive() on the same consumer.
- Good for: Event-driven services, Simple consumers, Less boilerplate

### listenerThreads
Number of threads available to execute MessageListener callbacks.

## Retry Topics

- When processing fails, instead of retrying immediately, pulsar can send the message to a Retry Topic. After delay, it again pushed to original topic for retry.
- Advantages : Delayed retry, Avoid hammering downstream systems, Better resilience

```

DeadLetterPolicy deadLetterPolicy =
        DeadLetterPolicy.builder()
                .maxRedeliverCount(5)
                .retryLetterTopic("orders-retry")
                .deadLetterTopic("orders-dlq")
                .build();

Consumer<String> consumer = client.newConsumer(Schema.STRING)
        .topic("orders")
        .subscriptionName("orders-sub")
        .enableRetry(true)
        .deadLetterPolicy(deadLetterPolicy)
        .subscribe();
        
// Processing     

try {
    process(message);
    consumer.acknowledge(message);
} catch (Exception e) {
    consumer.reconsumeLater(message, 30, TimeUnit.SECONDS);
}

```

### Exponential Backoff Retry

```

int retry = getRetryCount(message);

long delay =
        (long)Math.pow(2, retry);

consumer.reconsumeLater(
        message,
        delay,
        TimeUnit.SECONDS);

```

## Dead Letter Queue (DLQ)

After multiple retries, message goes to DLQ. It stores : Poison messages, Corrupted payloads, Permanently failing events.
- DLQs isolate poison messages that repeatedly fail processing. This prevents them from blocking the consumer while allowing engineers to inspect and reprocess them later.

## Retention

Retention policies determine how long acknowledged messages remain available for replay.

## 24. Questions

### Why is the Broker stateless?

Because all persistent data is stored in BookKeeper. Brokers only manage client connections, routing, topic ownership and message dispatch. Since they don't own storage, brokers can be added or removed with minimal impact.

### Why does Pulsar use BookKeeper?

BookKeeper is optimized for durable, replicated append-only storage. Offloading persistence from brokers improves scalability, resilience and enables independent scaling of compute and storage.

### How is ordering maintained?

Ordering is guaranteed within a partition. To preserve ordering for a business entity, producers publish all related events using the same message key so they are consistently routed to the same partition.

### What happens if a consumer crashes?

If the consumer crashes before acknowledging the message, the broker waits for the ACK timeout, then redelivers the unacknowledged message to another eligible consumer based on the subscription type. Since the message may be processed twice, consumers should be idempotent.

### Is Pulsar Push or Pull?

Push with Flow Control (Permits) : Pulsar is fundamentally push-based, but it implements flow control using consumer permits. The broker only pushes messages when the consumer has available permits, preventing it from being overwhelmed.

### How does Pulsar handle slow consumers?

Pulsar uses:
- Consumer permits
- Prefetch queue
- Flow control

### What happens if receiverQueueSize = 0?

No prefetch. Every receive() waits for Broker. Lower throughput.

### Can Pulsar replay messages?

Yes. Because messages remain in BookKeeper (subject to retention). Reset the subscription cursor and consume again.
- Common use cases : Rebuild cache, Re-index search, Recover after bug fix, Replay missed events

### Does Pulsar prevent duplicates?

Producer-side deduplication can prevent duplicate publishes caused by producer retries. However, consumer-side duplicates are still possible because of redelivery. Therefore, application-level idempotency is still required.

### Why use Retry Topics instead of immediate retries?

Immediate retries can repeatedly hit a failing downstream dependency. Retry Topics introduce a delay, giving external systems time to recover and preventing unnecessary load.

### With consumer.negativeAcknowledge(message), also goes to retry topic?

- The broker marks the message for redelivery.
- The message is not moved to a retry topic.
- The broker waits for the configured negative acknowledgment redelivery delay (the "nack timeout").
- After that delay expires, the broker redelivers the same message to a consumer (which could be the same or another consumer in a shared subscription).
- A retry topic is used only if you enable Retry Letter Topic. In this case, when processing fails and you negative acknowledge, it goes to retry topic.

| Feature                                  | Message goes to retry topic?                                                 |
|------------------------------------------|------------------------------------------------------------------------------|
| `negativeAcknowledge()` only             | ❌ No                                                                         |
| Ack timeout redelivery                   | ❌ No                                                                         |
| Retry Letter Topic (`enableRetry(true)`) | ✅ Yes                                                                        |
| Dead Letter Policy only                  | ❌ No (goes to DLQ only after max redeliveries, unless retry is also enabled) |

### If pulsar is pub sub, then how it is ensured that in distributed env, one message is consumed only once by a single node of service ?

In a distributed microservice deployment where multiple instances of the same service consume from a topic, we typically use a Shared Subscription (Load Balancing). The Pulsar broker load-balances messages across consumers in that subscription and delivers each message to only one consumer instance.
